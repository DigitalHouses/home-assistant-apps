# DH PVE Machine Events, UPS Status and Battery Semantics Design

Date: 2026-09-17
Status: proposed canonical amendment — approved in chat, pending written-spec review
Target: `dh_pve_app` on Proxmox VE 8.x
Branch: `feature/dh-pve-haos-trigger-v2`

## Authority

This document amends the canonical design in:

`docs/digitalhouses_pve_agent/specs/2026-09-15-dh-pve-simplified-runtime-haos-design.md`

It specifically supersedes the existing human-text event payload contract in sections 4, 8, 10, 14 and 15 wherever those sections require or allow `summary`, `details`, localized UPS status text, or other notification prose to be generated by `dh_pve_app`.

The line-power monthly statistics amendment remains authoritative for utility-power accounting:

`docs/digitalhouses_pve_agent/specs/2026-09-17-dh-pve-refresh-all-line-power-statistics-design.md`

Where this document is more specific, this document is authoritative for public event payloads, UPS normalized status, battery charger state, battery milestone events, fully-charged detection, and the HAOS notification boundary.

---

## 1. Goal

Make `dh_pve_app` a producer of machine semantics rather than user-facing notification text.

Canonical responsibility boundary:

```text
PVE / NUT
-> dh_pve_app acquisition + normalization + decisions
-> machine state + machine events
-> MQTT
-> HAOS localization + wording + emoji + notification policy
```

The same app must support a Russian, English, Kazakh or other HAOS package without Python changes.

## 2. Non-goals

- Do not move threshold decisions, outage accounting, shutdown authority or UPS interpretation into HAOS.
- Do not make HAOS reconstruct facts that the app can publish directly.
- Do not add battery charge milestones while the battery is charging.
- Do not expose arbitrary NUT commands, FSD commands, shell commands or UPS output-off actions through MQTT.
- Do not remove internal human-readable journal logging. Service logs may remain Russian and operationally useful.
- Do not require every existing non-event Lovelace presentation entity to be redesigned in this change. The hard machine-only rule applies to event/notification contracts and the machine state used by those contracts.

## 3. Machine-only public event contract

### 3.1 Prohibited event fields

`dh_pve_app` must not generate user-facing notification prose in MQTT Event payloads.

New event schemas must not contain fields whose purpose is presentation text, including:

```text
title
message
summary
details
recovery_message
localized_status
status_ru
emoji
```

The app publishes facts, identifiers, enums, values, timestamps and transition context.

Allowed strings include:

- stable machine enums such as `warning`, `online`, `boost`, `runtime_threshold`;
- source-native identifiers or names such as a configured guest name, storage ID, disk model or UPS model;
- raw NUT values/tokens preserved for diagnostics;
- exception class/error codes where required diagnostically.

### 3.2 Event schema version

Removing `summary/details` from the existing event contract is a breaking schema change.

All machine-only events defined by this amendment use:

```text
schema_version: 2
```

Do not silently change the meaning of schema version 1.

### 3.3 Previous/current rule

Whenever an event represents a state transition, publish both the previous and current machine state whenever both are known.

This is preferred over app-generated phrases such as `started`, `ended`, `restored` or `OK` because HAOS can derive any desired presentation from the transition.

For first observation after startup, `previous` may be absent/null if the app has no persisted authoritative previous state. The app must not fabricate a transition merely to populate an event.

### 3.4 Timestamp

Every event includes an app-observed timezone-aware timestamp:

```text
observed_at
```

The timestamp is data. HAOS owns formatting it for the user's locale.

## 4. Generic problem events v2

Existing problem binaries remain current-state contracts. Problem events become machine-only.

Canonical problem event shape:

```yaml
schema_version: 2
event_type: problem_started | problem_recovered | problem_updated
observed_at: <timezone-aware ISO timestamp>
problem_id: cpu_temperature
category: cpu
severity: warning
object_id: cpu
metric: temperature_c
previous:
  active: false
  value: 76.0
  average: 75.4
  threshold: 80.0
current:
  active: true
  value: 84.0
  average: 81.2
  threshold: 80.0
active_problem_count: 1
```

For discrete problems, numeric fields may be absent/null as appropriate.

The event must not contain `summary` or `details`.

HAOS may render the example above as any localized text it chooses. It must not reread multiple entities to discover the current value/average/threshold when the event already carries them.

---

## 5. Retained problem aggregate/presentation state

The app remains responsible for determining which problems are active and for publishing a coherent retained aggregate. HAOS must not wildcard-scan dynamic problem binaries to calculate the aggregate.

However, retained aggregate data used by HA presentation must be structured and non-localized.

Target shape:

```yaml
count: 2
severity: critical
active:
  - problem_id: disk_sda_smart
    category: disk
    object_id: sda
    metric: smart_passed
    value: false
  - problem_id: cpu_temperature
    category: cpu
    object_id: cpu
    metric: temperature_c
    value: 84.0
    average: 81.2
    threshold: 80.0
```

Remove generated prose such as:

```text
No active problems
1 active problem
CPU temperature high
CPU temperature OK
Average 81.2 C; threshold 80 C
Работа от батареи: OK
```

The aggregate state remains app-owned; its human wording becomes HAOS-owned.

## 6. UPS normalized status model

### 6.1 Raw NUT status remains source evidence

Preserve the raw ordered NUT `ups.status` tokens for diagnostics.

The parser must tolerate unknown future tokens without failure.

### 6.2 Canonical UPS status set

Normalize recognized UPS status tokens to stable machine enums:

```text
OL       -> online
OB       -> on_battery
LB       -> low_battery
HB       -> high_battery
RB       -> replace_battery
BYPASS   -> bypass
CAL      -> calibration
OFF      -> output_off
OVER     -> overload
TRIM     -> trim
BOOST    -> boost
FSD      -> forced_shutdown
ALARM    -> alarm
```

`CHRG` and `DISCHRG` are not part of the canonical UPS status set in the new contract. They belong to battery charger-state interpretation and remain available in `raw_status_tokens` for fallback/diagnostics.

This follows current NUT semantics: `OL`/`OB` represent line-input state, while historic `CHRG`/`DISCHRG` flags are being replaced by `battery.charger.status`.

### 6.3 Status sensor

`sensor.dh_app_pve_ups_status` remains useful for Recorder/Logbook, but its public state/attributes must be machine-oriented rather than localized by the app.

At minimum expose:

```text
status              # normalized machine state suitable for the sensor state
status_set           # complete normalized set
raw_status_tokens    # complete raw NUT token set
```

Do not publish `status_ru` from the app in the new contract. HAOS maps normalized values to localized text.

Exact single-value `status` precedence is an implementation detail that must be deterministic and test-covered. The complete `status_set` remains authoritative when multiple simultaneous conditions exist, e.g. `online + boost`.

## 7. UPS status-change event

Publish one machine event whenever the canonical UPS status set changes.

Canonical payload:

```yaml
schema_version: 2
event_type: ups_status_changed
observed_at: <timezone-aware ISO timestamp>
previous_status:
  - on_battery
current_status:
  - online
previous_raw_status:
  - OB
  - DISCHRG
current_raw_status:
  - OL
```

For another example:

```yaml
previous_status:
  - online
current_status:
  - online
  - boost
previous_raw_status:
  - OL
current_raw_status:
  - OL
  - BOOST
```

HAOS can therefore independently decide whether to notify about:

- loss/restoration of utility power;
- bypass enter/exit;
- boost enter/exit;
- trim enter/exit;
- overload enter/exit;
- low-battery enter/exit;
- replace-battery state;
- FSD appearance;
- alarm appearance/removal;
- calibration or output-off changes.

The app does not attach wording to any of these transitions.

### 7.1 No duplicate semantic events

One real UPS status transition must not produce both a generic `problem_started/problem_recovered` notification event and a parallel `ups_status_changed` event for the same status-derived fact.

Status-derived retained problem binaries may remain for current-state diagnostics/UI, but notification transport for UPS status tokens is `ups_status_changed`.

Generic UPS problem events remain appropriate for facts not represented by a trustworthy `ups.status` transition, such as NUT communication unavailable or app-specific diagnostic failures.

## 8. Canonical battery charger status

### 8.1 New entity

Add under the existing UPS device:

```text
sensor.dh_app_pve_ups_battery_charger_status
```

Canonical values:

```text
charging
discharging
floating
resting
idle
unknown
```

`idle` is a fallback-derived state meaning that the app currently observes neither charging nor discharging from legacy status evidence; it must not be presented as equivalent to NUT-native `resting`.

### 8.2 Source priority

Determine charger status in this order:

```text
1. valid NUT battery.charger.status
2. legacy ups.status CHRG / DISCHRG fallback
3. line power present + no CHRG/DISCHRG -> idle fallback
4. otherwise unknown
```

Direct NUT values map as:

```text
charging    -> charging
discharging -> discharging
floating    -> floating
resting     -> resting
```

Unknown direct values must not be guessed; expose `unknown` and preserve the raw value diagnostically.

### 8.3 Existing charging/discharging binaries

Keep existing `charging` and `discharging` binary sensors for compatibility where practical, but derive them from the canonical charger-state resolver rather than independent logic:

```text
charger_status == charging    -> charging ON
charger_status == discharging -> discharging ON
all other canonical states    -> corresponding binary OFF
unknown                       -> unavailable/unknown according to Discovery contract, not false certainty
```

### 8.4 UI

The standard UPS dashboard must expose the canonical charger status with an icon/text mapping in HAOS.

Localization belongs to the dashboard/package. Example Russian mappings may be:

```text
charging    -> Заряжается
floating    -> Поддержание заряда
resting     -> Заряжена
idle        -> Ожидание
discharging -> Разряжается
unknown     -> Неизвестно
```

These strings are HAOS presentation examples, not app payload values.

## 9. Battery discharge milestone events

### 9.1 Thresholds

The app-owned milestone set is:

```text
90, 80, 70, 60, 50, 40, 30, 20, 10 percent
```

These are notification milestones, not shutdown thresholds and not user-configurable policy values.

### 9.2 Crossing semantics

Do not require an exact battery percentage.

Example:

```text
previous charge = 94
current charge  = 87
```

This crosses the 90% milestone and emits an event.

Canonical payload:

```yaml
schema_version: 2
event_type: battery_discharge_level_crossed
observed_at: <timezone-aware ISO timestamp>
previous_charge_percent: 94
current_charge_percent: 87
crossed_thresholds:
  - 90
```

A large sample jump emits one event, not a burst:

```text
94 -> 67
crossed_thresholds = [90, 80, 70]
```

HAOS receives one event and can render one current notification.

### 9.3 Discharge only

Do not emit 20/30/.../90 milestone events while the battery charges upward.

A downward threshold event is valid only when the UPS is in an authoritative battery-use context, primarily confirmed `on_battery`/line-power OFFLINE. Canonical charger status may strengthen this evidence but must not make support depend on a driver exposing `battery.charger.status`.

A small estimator correction while utility power is present must not generate a discharge milestone notification.

### 9.4 Persistent outage/discharge session

Persist enough session state to prevent duplicates across app restarts during an outage, including at least:

```text
session_active
session_started_at
last_observed_charge_percent
emitted_thresholds
```

Start/reset a new discharge session on a trustworthy transition into `on_battery`.

Close the session on trustworthy return to `online`.

If the app starts already on battery with no authoritative previous charge above a threshold, do not invent a crossing event. Establish the current baseline and emit only future observed crossings. If persisted session state proves a crossing occurred across a restart interval, handle it once according to persisted previous/current evidence.

## 10. Fully charged event

### 10.1 Meaning

`battery_fully_charged` means:

> the app observed completion of a battery charge cycle

It does **not** mean `battery.charge == 100` is mandatory.

Battery charge percentage is measurement/estimate data and may legitimately stop below 100 on some UPS/driver combinations.

### 10.2 Preferred detection

When `battery.charger.status` exists, a completed charge cycle is detected from a real charger transition such as:

```text
charging -> floating
charging -> resting
```

Emit once per observed charging cycle.

A later `floating -> resting` transition must not emit a duplicate fully-charged event if the same cycle already produced one.

### 10.3 Legacy fallback

When `battery.charger.status` is unavailable, use legacy status evidence conservatively:

```text
previous observation: OL + CHRG
current observations:  OL, no CHRG, no DISCHRG
```

Require the completed state to be stable across consecutive UPS samples before emitting the fallback event, so a one-sample token flap does not create a false completion event.

The exact confirmation count is implementation detail but must represent at least two consecutive 10-second observations.

### 10.4 Payload

```yaml
schema_version: 2
event_type: battery_fully_charged
observed_at: <timezone-aware ISO timestamp>
previous_charge_percent: 97
current_charge_percent: 98
previous_charger_status: charging
current_charger_status: floating
detection_source: charger_status
```

Fallback example:

```yaml
event_type: battery_fully_charged
previous_charge_percent: 96
current_charge_percent: 98
previous_charger_status: charging
current_charger_status: idle
detection_source: legacy_status_fallback
```

The charge values may be null if the UPS does not expose trustworthy percentages.

### 10.5 Startup behavior

Do not emit `battery_fully_charged` merely because the app starts and first observes `resting`, `floating`, `idle` or `100%`.

A real charging-cycle transition must have been observed or persisted.

## 11. Shutdown commitment event

Software shutdown commitment is a distinct app decision and must not be conflated with the NUT `FSD` status token.

When the local software controller first commits shutdown, publish exactly one machine event before shutdown proceeds as far as delivery is still possible:

```yaml
schema_version: 2
event_type: shutdown_committed
observed_at: <timezone-aware ISO timestamp>
reason: runtime_threshold
battery_charge_percent: 43
battery_runtime_seconds: 390
shutdown_budget_seconds: 220
runtime_reserve_seconds: 180
runtime_guard_threshold_seconds: 400
```

Possible reason codes must be stable machine enums, e.g.:

```text
charge_threshold
runtime_threshold
```

Native NUT Low Battery/FSD remains visible through normalized UPS status/events and the existing shutdown-history evidence path. Do not relabel native `FSD` itself as the app's `shutdown_committed` event.

HAOS chooses the critical notification wording.

## 12. Policy config-change event v2

Successful UPS policy apply remains an event, but remove human prose.

Target shape:

```yaml
schema_version: 2
event_type: config_changed
observed_at: <timezone-aware ISO timestamp>
category: policy
object_id: ups_trigger_policy
old_values:
  shutdown_battery_charge_threshold_percent: 20
  runtime_reserve_seconds: 180
new_values:
  shutdown_battery_charge_threshold_percent: 25
  runtime_reserve_seconds: 240
previous_revision: 3
current_revision: 4
```

No app-generated `summary/details`.

HAOS is responsible for rendering meaningful OLD -> NEW text.

Failed apply/rollback remains a failure state, not a successful `config_changed` event. Expose machine result/reason codes in state where needed and retain detailed human operational diagnostics in the service journal.

## 13. HAOS notification responsibility

HAOS owns:

```text
language
localized labels
message title/body
emoji
notification channel
gating
repeat policy
quiet-hours/site policy
which machine events are user-visible
```

Examples of HA-side decisions:

```text
ups_status_changed: on_battery -> online
=> "Городское питание восстановлено"

battery_discharge_level_crossed: current=87, crossed=[90]
=> "UPS: заряд снизился до 87%"

battery_fully_charged
=> "UPS: батарея полностью заряжена"

shutdown_committed
=> critical shutdown notification
```

These examples are not part of the app protocol.

HA should consume the event payload directly rather than rereading multiple state entities to reconstruct the event.

## 14. MQTT Event surface

Keep the existing MQTT Event transport unless implementation evidence requires a separate migration:

```text
event.dh_app_pve_diagnostic
event.dh_app_pve_ups_diagnostic
```

Expand the UPS Event entity's allowed event types to include at least:

```text
problem_started
problem_recovered
problem_updated
config_changed
ups_status_changed
battery_discharge_level_crossed
battery_fully_charged
shutdown_committed
```

Runtime Event messages remain:

```text
QoS 1
retain = false
```

Retained state remains the current-state source. Events remain transition/notification transport.

## 15. Migration from event schema v1

### 15.1 HA-first compatibility deployment

To avoid a notification gap during upgrade:

1. update the HA package/automation first so it can parse both event schema v1 and v2;
2. deploy the app version that emits schema v2 machine events;
3. verify v2 event reception and notification formatting;
4. remove temporary v1 HA compatibility only in a later cleanup after production evidence.

Do not require the app to dual-publish v1 and v2 events; that would create duplicate notifications.

### 15.2 Discovery migration

If MQTT Discovery templates/event type metadata change, bump the app's Discovery schema/versioned manifest as required and republish the Event entities idempotently.

### 15.3 Retained state migration

Overwrite existing retained problem-presentation/status payloads with the new structured machine form. If Discovery templates reference removed localized fields such as `status_ru`, update them in the same reviewed release.

## 17. Test contract

Use TDD.

### 17.1 Machine-event schema

Tests must prove:

- schema v2 event payloads contain no `title`, `message`, `summary`, `details`, `recovery_message`, `status_ru` or emoji fields;
- generic problem events contain previous/current structured state;
- first observation does not fabricate a transition;
- timestamps are timezone-aware;
- event transport remains QoS 1 and non-retained;
- one semantic UPS status transition does not emit duplicate status-derived problem notification events.

### 17.2 UPS normalization

Tests must prove:

- all recognized NUT status tokens normalize correctly;
- unknown raw tokens are preserved without parser failure;
- CHRG/DISCHRG are separated from the canonical UPS status set;
- `battery.charger.status` takes priority over CHRG/DISCHRG;
- fallback charger states are deterministic;
- invalid/unknown direct charger values become `unknown`, not guessed native states;
- `sensor.dh_app_pve_ups_battery_charger_status` Discovery/state contract is stable.

### 17.3 UPS status events

Tests must prove:

- previous and current canonical status sets are emitted;
- previous and current raw token sets are emitted;
- OL -> OB and OB -> OL emit immediately;
- BOOST/BYPASS/TRIM/OVER/LB/RB/FSD/ALARM transitions are represented without app-generated prose;
- unchanged status sets do not emit events;
- restart first observation does not fabricate `ups_status_changed` without authoritative previous state.

### 17.4 Battery discharge milestones

Tests must prove:

- 94 -> 87 while on battery emits `[90]`;
- 94 -> 67 emits one event with `[90, 80, 70]`;
- exact threshold equality is treated as crossing when moving from above to equal/below;
- repeated samples below an already-emitted threshold do not duplicate the event;
- charging upward emits no milestone event;
- online estimator drift emits no discharge milestone event;
- restart during an outage preserves already-emitted thresholds;
- startup already below a threshold without authoritative crossing evidence does not fabricate an event.

### 17.5 Fully charged

Tests must prove:

- direct `charging -> floating` emits once;
- direct `charging -> resting` emits once;
- subsequent `floating -> resting` does not duplicate the same cycle;
- first startup observation `resting`/`floating`/100% emits nothing;
- fallback CHRG disappearance while OL requires stable consecutive confirmation;
- fallback token flap does not emit;
- fully charged may emit with charge below 100%;
- direct charger status wins over conflicting legacy CHRG/DISCHRG evidence.

### 17.6 Shutdown/config events

Tests must prove:

- software shutdown commitment emits exactly once with structured reason/current values;
- NUT FSD is not relabeled as app software commitment;
- successful policy config change publishes OLD/NEW/revision data without prose;
- failed apply/rollback does not emit a successful config-change event.

### 17.7 HA package/UI

Validator/manual tests must prove:

- HA v2 automation formats localized notification text from machine fields;
- temporary migration automation accepts v1 and v2 without duplicate delivery;
- charger-status icon/text reads the canonical charger-status entity;
- no HA wildcard scan is introduced to reconstruct transitions;
- notification text can be changed/language-swapped without modifying Python.

## 18. Failure and retry semantics

Event publication must preserve the existing retained-state-before-event ordering where applicable.

A failed MQTT event publish must be retryable without:

- duplicating battery milestones;
- resetting a discharge session;
- duplicating fully-charged cycle completion;
- duplicating shutdown commitment;
- advancing transition baselines incorrectly.

Persist semantic deduplication state before or transactionally with the retry path as required by each event type.

Do not mark an event as successfully delivered merely because the local decision occurred; transport success and local semantic state are distinct facts.

## 19. Freeze invariants

This amendment freezes the following rules:

```text
app events are machine semantics, not user prose
HAOS owns notification language/text/emoji
schema v2 is required for the breaking machine-event contract
transition events carry previous + current when authoritative
problem events contain structured values, not summary/details
retained problem aggregate is structured and non-localized
UPS status events carry complete previous/current normalized sets
raw NUT tokens are preserved diagnostically
CHRG/DISCHRG belong to charger-state fallback, not canonical UPS status
battery.charger.status is the preferred charger source
canonical charger status is exposed in the standard UPS UI
battery milestones are discharge-only: 90..10 by tens
crossing means previous above threshold and current equal/below threshold
multiple crossed thresholds in one sample produce one event
milestone session state survives app restart
fully charged means observed charge-cycle completion, not necessarily 100%
startup at full charge does not fabricate a fully-charged event
software shutdown_committed is distinct from NUT FSD
config_changed publishes machine OLD/NEW data only
one semantic UPS transition must not create duplicate notification events
internal journal logs may remain human-readable
no destructive UPS validation is authorized by this feature
```

Any future change to these invariants requires an explicit design revision before implementation.
