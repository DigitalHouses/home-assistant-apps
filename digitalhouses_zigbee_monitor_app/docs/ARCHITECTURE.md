# DH Zigbee Monitor — архитектурный черновик

Статус: **design draft**, 2026-10-18. Не является работающим HAOS App.

## Границы ответственности

```text
Zigbee2MQTT #1..N  --MQTT-->  HAOS App (Python)
                                   |
             +---------------------+--------------------+
             | Device / Network Registry (stable IDs)   |
             | Offline / Network-health Engine          |
             | MQTT Traffic Counters / Spam Analytics   |
             | Incident Engine / Event Queue            |
             | SQLite aggregates / incident history     |
             +---------------------+--------------------+
                                   |
                      MQTT Discovery + retained state
                                   |
                           Home Assistant UI
                        Recorder (скалярные метрики)
                         local notification package
```

- HAOS App использует Supervisor MQTT Service; секреты не находятся в Dashboard.
- В конфигурации — список сетей с **неизменяемым** `network_id` и текущим `base_topic`.
  Переименование `base_topic` не должно обнулять историю.
- `bridge/devices` — источник принадлежности устройств и их IEEE.
  Zigbee2MQTT `availability` — основной источник online/offline.
- Состояние каждого источника отделяется от состояния отдельных устройств.
  Проблема MQTT, остановка Zigbee2MQTT и реальный offline — разные факты.
- Штатное Zigbee2MQTT availability должно быть включено на каждом экземпляре:
  App проверяет наличие и свежесть этой информации, но не пытается самостоятельно Zigbee-ping.
- Без auto-healing, перезапуска Zigbee2MQTT, power-cycle или изменения reporting в v0.1.0.

## Реальный INCIDENT-001: Bridge online ≠ Zigbee исправен

В предыдущем проекте Zigbee Boss **наблюдалось зависание**, при котором
Zigbee2MQTT продолжал сообщать `online`, ошибок в его журнале не было,
но Zigbee-устройства фактически переставали отвечать. Это причина
введения персонального мониторинга MQTT RPM по сети как **отдельного**
индикатора скрытого отказа. RPM должен работать независимо от
`bridge_offline`, `devices_offline`, а будущие health/проверки
не заменяют его. Низкий RPM не доказывает аппаратную причину и сам
по себе не даёт разрешения для Healer.

**Каноническая запись, ограничения, тест и контекст будущих чатов:**
[KNOWN_FAILURE_SCENARIOS.md](KNOWN_FAILURE_SCENARIOS.md).

## Стабильная идентичность

- Физический Zigbee-девайс: нормализованный `ieee_address`.
- Сеть: конфигурационный `network_id`, не имя/положение/топик.
- Наблюдение: пара `(network_id, ieee_address)`.
- История одного физического устройства может пережить перенос между сетями;
  нужно сохранить временной интервал принадлежности сети.
- `friendly_name`, MQTT state/availability topic и HA entity IDs — изменяемые связи,
  обновляемые при новом inventory. Нельзя создавать новую историю только из-за переименования.
- Если устройство исчезло из инвентаризации, не объявлять его восстановленным
  или физически неисправным без данных; предусмотреть отдельно `removed`/неизвестность.

## Модель доступности

Предлагаемые состояния наблюдения:
`online`, `offline_pending`, `offline_confirmed`, `unknown`, `source_unavailable`.

Точная бизнес-логика и периоды задержек согласуются на основании реальных Z2M.
Инциденты включают наблюдения, подтверждение, восстановление, длительность,
`incident_id` и защиту от повторов после рестартов.

Массовое отключение при потере Zigbee2MQTT становится **инцидентом сети**,
а не десятками повторяющихся уведомлений о конечных устройствах.
Отдельные статусы устройств сохраняются для диагностики.

## Хит-парад MQTT-активности

Две разные функции:

1. **ТОП активности** — абсолютное количество сообщений по IEEE, за 1ч/24ч/7д;
   возможна группировка по модели, производителю и сети.
2. **Спам / аномальность** — выход относительно baseline того же устройства,
   только после достаточного количества наблюдений.

MQTT retained replay, публикации самого `bridge`, сервисные топики и
повторная доставка при reconnect **не должны автоматически считаться**
новым сообщением Zigbee-устройства.

Приложение агрегирует сообщения в памяти, периодически сохраняет временные
корзины в SQLite под `/data`; не сохраняет каждое MQTT-сообщение отдельно.
Нужны bounded queues, контроль пропусков и диагностика невозможности точного счёта.

SQLite: таблицы сетей, устройств/переименований, агрегатов активности,
инцидентов, pending event outbox и метаданных схемы. Ретеншн — отдельное
обязательное решение перед реализацией и backup acceptance.

## Публикация и события

- MQTT retained — только достоверное актуальное состояние/диагностика,
  а не фиктивная свежесть; MQTT LWT и явная доступность источников.
- Машинные переходные события — MQTT Event Discovery, QoS 1, retain false.
- Сначала фиксируется и публикуется текущее состояние, затем событие.
- Человекочитаемые уведомления — локальный HA-пакет по стандарту Events;
  публичный App не знает `script.write2admins` и `script.write2log`.
- Поля событий строго валидируются; нельзя подменять пропущенное значение нулём.
- Состояние операций App использует общую status-card state machine;
  Supervisor управляет установкой обновлений и рестартом контейнера.
