# Aqara Switch · Полевые уроки, электрическая топология и восстановление питания

**Дата фиксации:** 2026-10-21  
**Источник:** обсуждение требований после многократного ввода реальных объектов в эксплуатацию.  
**Статус:** продуктовые требования и исследовательский backlog; **не считать реализованным функционалом**.

> Главное требование: приложение должно делать удобными *ввод объекта в эксплуатацию, ежедневную эксплуатацию, обслуживание, замену оборудования и восстановление после аварии*, а не только обрабатывать нажатия.
>
> **Не терять эти сценарии при рефакторинге и развитии проекта.**

## 1. Разделяем подтверждённые решения и открытые гипотезы

Здесь:
- **Согласовано** — ожидаемый контракт продукта; его реализация и приёмка могут ещё отсутствовать.
- **Исследовать** — важная мысль из практики, пока не принято окончательное архитектурное решение.
- **Аппаратный gate** — нельзя безопасно реализовать без испытаний конкретной модели/прошивки.

Изложенные ниже алгоритмы **не активированы** в экспериментальной версии 0.1.1. Никакие реальные реле не должны включаться только потому, что требования описаны в этом документе.

## 2. Жизненный цикл выключателя (согласовано)

**Первичная установка**:
1. Монтаж и подключение Aqara.
2. Сопряжение с Zigbee2MQTT и ручная настройка в Z2M (режимы кнопок/реле, индикатор, power-on и другие поддерживаемые параметры).
3. Пользователь вручную запускает «Сканировать» в HA.
4. App импортирует **только новые** логические выключатели и фиксирует подтверждённые физические настройки как эталон. **При первом импорте ничего не записывать в Zigbee-устройство.**
5. Назначения клавиш и электрические связи заполняются отдельно.

**Повторное сканирование**: существующая логическая запись остаётся **полностью неизменной** (в том числе эталон режимов, комната, назначения, электрические связи); отсутствующие/offline устройства не удаляются. Сканирование — отдельная ручная операция, не стартовая, не фоновая и не «Обновить».

**Переустановка/замена**:
- Постоянна *логическая идентичность* (сеть / логическое имя Zigbee2MQTT); IEEE — текущая аппаратная привязка, которая может измениться после замены.
- Пользователь может спарить новый экземпляр Aqara с прежним friendly_name: назначения клавиш/нагрузок не должны теряться.
- Существует только два исхода проверки нового экземпляра: **полностью совместимый профиль** (модель, endpoints, число клавиш/реле, actions, параметры управления) → разрешить перепривязку и впоследствии восстановление эталона; **существенное отличие или неоднозначность** → проблема, остановка автоматических изменений, разбирательство.
- Значения заводских настроек нового *совместимого* экземпляра могут отличаться от сохранённого эталона — именно их впоследствии должен привести к эталону Mode Keeper, **после безопасного подтверждения возможностей устройства**.
- Не считать замену HA MQTT-устройства автоматической гарантией сохранения его \`entity_id\`: Registry может создать суффикс \`_2\`; требуется отдельная проверка/reconciliation. Приложение не должно молча переписывать чужие HA-сущности.
- Перенос между разными Zigbee-сетями/координаторами — отдельный ещё не согласованный процесс миграции, не маскировать его под совпадение имён.

**Эксплуатация**:
- Dispatcher обслуживает только настроенные действия и не дублирует старый AQPM2 до явного cutover.
- Mode Keeper проверяет и возвращает только поддерживаемые и достоверно наблюдаемые физические настройки; unknown не считать OK.
- Maintenance Mode временно переводит *нужные* клавиши/выходы в физический режим для питания/сопряжения умных ламп, затем восстанавливает **индивидуальный** эталон; при неудаче показывает проблему. Батареечные кнопки не получают несуществующие реле.
- Удаление из приложения **не** удаляет устройство из Zigbee2MQTT. Во время активного Maintenance/незавершённого восстановления удаление блокируется.

## 3. Где редактируем настройки, а где работаем (согласовано)

**Конфигурация:** единственный источник редактируемых данных — **Supervisor App Options**, модель **комната → выключатель**, без глобальных дублирующих справочников settings/actions/electrical. Текущий пилот хранит вложенную структуру в одном поле \`configuration_yaml\` из-за ограничений глубины Supervisor.

**Оперативный UI:** обычный Home Assistant Dashboard в стиле \`dh_zigbee_monitor_app\`, **не Ingress**.
- Обязательная стандартная **карточка управления приложением**: состояние, версия, проверка версии/обновление, реальная установка, перезапуск, операции; не показывать фиктивные работающие кнопки, если backend ещё не готов.
- **Дерево:** комната → выключатель; внутри выключателя ветви клавиши/команды, индивидуальные режимы, логические светильники/группы, электрические выходы и их нагрузки, проблемы, обслуживание.
- **Результаты последнего ручного сканирования:** время, найденные, добавленные, пропущенные, ошибки; сохранять через рестарт; возможность перейти к найденному выключателю.
- **Ссылки в HA-дереве:** переход к выключателю/группе; перспектива назначения светильников прямо из UI.
- **Удаление по 🗑️ ссылке в дереве, обязательно с подтверждением.** Обычный Markdown не поддерживает произвольный подтверждаемый action для каждой гиперссылки; подобрать безопасный HA UI-компонент/ссылочный маршрут, испытать на домашнем стенде. Не подменять подтверждение одной ссылкой, которая удаляет без диалога.
- Статусы и причины проблем принадлежат Python App; HA — презентация. Данные дерева/последнего импорта можно публиковать структурированными сенсорами без сущности для каждой клавиши. Не использовать \`tojson\` в HA templates.

**Важно:** пилотная версия 0.1.1 уже имеет **часть** сканирования/карточек, но ссылки для назначения и подтверждённого удаления, полный product status и Dispatcher ещё не готовы.

## 4. Три независимые связи: управление, Zigbee-группы, электричество (согласовано)

Эти связи **никогда не подменяют друг друга**:

1. **Управление:** клавиша Aqara в \`decoupled\` → Z2M группа / direct Zigbee binding / поддерживаемая команда HA (механизм выбирается/подтверждается отдельно). В типичном объекте освещение уже объединено в **Zigbee-группы**.
2. **Членство в группе:** Z2M группа → участники-светильники и endpoint'ы. **Читать из Zigbee2MQTT**, не копировать вручную списки членов в каждую запись выключателя.
3. **Электропитание:** щитовое DIN-реле → питание Aqara → физическое выходное реле Aqara → один или несколько светильников/обычных нагрузок. Это **описанная монтажная топология**, независимо от того, на какую группу отправляет команду клавиша.

На одном выключателе:
- \`panel_relay\` — опциональная **ссылка на HA-сущность** щитового реле, например \`switch.tongou_livingroom_lights\`. **Не привязывать фазу в Aqara App**.
- \`outputs\` — будущий список реальных *каналов физических выходных реле Aqara*. У каждого — \`powered_lights\` или, шире, \`powered_loads\`, которые **электрически** питаются от данного канала. Одно реле может питать несколько светильников.
- Нагрузке может хватать постоянного логического ID и имени: не каждый обычный светильник существует как \`light.*\` в HA; его entity_id необязателен.
- Для батареечных кнопок физических выходов нет. Не создавать фиктивные выходы.
- Один Zigbee group может объединять лампы, питающиеся от разных выходов и DIN-реле. И наоборот, один физический выход может питать членов нескольких логических групп.

**Граница приложений**:
- \`dh_aqara_switch_app\` — выключатели, их physical outputs, привязки к группам, ссылки на входные DIN-реле, Mode Keeper, Maintenance, каскад восстановления **его** выходов.
- **Планируемый** \`dh_tongou_app\` — структура щита, линии/фазы/автоматы/DIN-реле и их статус. В Aqara App не копировать фазы и электротопологию щита.
- \`dh_zigbee_monitor_app\` — наблюдение сети и проблемы, **не управление** устройствами.
- В будущем электрическая карта объекта собирается по этим контрактам, без ручного дублирования данных о членстве групп или фазах.

## 5. Два режима после отключения электричества (важное новое требование)

### 5.1 Hardware restore (аппаратный)

Существующее устройство восстанавливает выходы согласно собственным Zigbee/firmware settings (\`power_on_behavior\`, \`power_outage_memory\` и т. п.). App не управляет порядком появления питания.

Этот вариант остаётся необходимой штатной политикой там, где каскад невозможен или нежелателен (например, важное освещение).

### 5.2 Cascade restore (программный каскад)

**Цель:** восстановить питание *самих* выключателей и необходимой инфраструктуры Zigbee раньше, чем массово подавать питание на умные светильники. Переждать массовое подключение устройств («Zigbee storm») и затем по очереди запитать физические выходы, работающие по выбранной политике каскада.

Потенциальная последовательность:
1. После подтверждённого **реального события потери/возврата сети** DIN-реле (если оно участвует) восстанавливает питание необходимого для управления оборудования.
2. Aqara поднимаются **с физическими выходами OFF**. Это должно обеспечиваться **аппаратной настройкой конкретной модели**, пока HA и Z2M ещё недоступны.
3. Ждём готовности нужных Z2M сетей/координаторов и минимальной стабилизации, с тайм-аутами и проверкой связи с конкретным Aqara. \`bridge online\` само по себе не гарантирует успокоения сети; низкий/высокий MPM тоже не самостоятельный доказанный критерий.
4. App последовательно отправляет команды включения физическим выходам, определённым как каскадные; проверяет подтверждение фактических состояний. Порядок, интервалы, приоритеты, ретраи, останов и восстановление незавершённой операции — параметры будущего контракта.
5. После включения питания умных ламп возвращаемся к обычному контролю режимов и логических команд, **не** трактуем \`decoupled\` как «реле обязательно ON»: режим кнопки и состояние реле — независимы.

**Safety gates перед реализацией**:
- Если конкретная Aqara не гарантирует boot relays OFF без программной помощи, для такого выхода **cascade не активировать**. \`power_outage_memory\` и «last state» не равны «always OFF».
- **Обычный перезапуск HA/Z2M или MQTT reconnect не запускает каскад**, когда питание не пропадало. Нужен надёжный признак power-restoration или явное управляемое вмешательство.
- При отказах/неопределённости нельзя объявлять полный успех или хаотично включать все реле. Должна быть понятная ошибка и ручная процедура восстановления/остановки.
- Не создавать зависимости, когда для запуска Zigbee нужно включить нагрузку, которую каскад удерживает OFF: учитывать запитываемые маршрутизаторы и оборудование управления.
- Порядок разрабатывается на основании **физических выходов** и доступности питания, а не только имен Zigbee-групп.
- Рассмотреть разные политики для разных каналов **одного** многоканального Aqara.
- Никаких тестов с реальными нагрузками до приёмки стенда, конфигурации и поведения при обесточивании.

## 6. Дополнительная проблема: smart-light startup behavior (исследовать)

**Наблюдение:** в большинстве проектов умные светильники объединены в Zigbee-группы, а клавиша Aqara в \`decoupled\` управляет **группой**. Но \`power_on_behavior\` / startup-модели задаются **для каждого индивидуального светильника**, не для группы как одного виртуального прибора.

Для управляемого включения после каскада требуется:
- Групповая политика вида «после восстановления питания участники не зажигаются автоматически».
- Раскрытие **фактического** состава Z2M группы (например, из \`bridge/groups\`), включая endpoint'ы.
- Для каждого участника проверка модели, \`exposes\`, допустимых значений и *текущего подтверждённого* параметра; применение только совместимых настроек, проверка результата, диагностика неподдерживаемых устройств.
- Не интерпретировать «группа OFF» как доказательство того, что все лампы поддерживают/сохраняют \`power_on_behavior: off\`.
- Не полагаться на одну глобальную маску \`select.*_power_on_behavior\`: совпадение имен не подтверждает совместимость устройства, принадлежность группе или допустимость значения.
- Возможны **профили/маски** как удобная форма пользовательского указания политики, но их scope должен быть ограничен явно выбранной группой и её проверенными членами; до записи можно показывать dry-run. При конфликте политик для светильника из нескольких групп — проблема, не запись наугад.
- Следить за **новым участником или заменой лампы**: установка политики должна происходить на новом оборудовании, а не требовать переобучения/пересканирования выключателя.
- Если лампа не поддерживает аппаратный startup OFF, программное отключение после загрузки **не гарантирует отсутствия вспышки**.
- Startup OFF у ламп **не предотвращает** загрузку/переподключение радио при подаче питания — для снижения массового переподключения нужен каскад питания.

### 6.1 Граница Light Startup Keeper — ОТКРЫТОЕ архитектурное решение

**Проблема:** если Light Startup Keeper разместить в \`dh_aqara_switch_app\`, возникает неявное владение жизненным циклом Zigbee-групп и светильников приложением выключателей, хотя группой могут управлять несколько выключателей/другие интеграции и её члены могут физически питаться по разным цепям.

**Предварительное направление, не окончательное решение:** отдельный небольшой сервис/приложение светильников, которое владеет Z2M группами и индивидуальными power-on настройками их членов. Aqara App тогда хранит **ссылки** на группы и физическую топологию, а не дублирует перечни членов или их startup параметры.

**Не создавать новое приложение сейчас только ради идеи.** После домашнего E2E \`Aqara → Zigbee-группа\` решить, нужна ли самостоятельная компонента по реальным потребностям и стоимости сопровождения. Если этого можно достичь без нового владельца конфигурации — предпочесть простоту.

## 7. Что проверяем дома (согласованный испытательный путь)

На домашнем объекте **ещё нет полноценного комплекта умных светильников и выключателей**. Возможно, есть батареечная кнопка Aqara; её модель и наличие ещё не подтверждены.

1. Добавить три виртуальных \`light.dh_aqara_lab_*\` с независимыми \`input_boolean\` (пример HA package уже в репозитории); проверить ручное включение.
2. Найти реальную Aqara кнопку в Z2M, определить модель и действительно доступные \`action\` события.
3. Проверить ручной Scan, комнату/обнаружение, результат последнего импорта, идемпотентность, HA дерево, диагностику.
4. Привязать нажатие к виртуальным светильникам; E2E без физических реле и без двойного Dispatcher.
5. Отдельно тестировать логическую группу Z2M только если есть реальные Zigbee-участники; **HA template lights не являются Zigbee group members**.
6. Замены/Mode Keeper/физические выходы/электрический power-cycle/cascade/startup keeper — отдельные аппаратные испытания, не имитировать успешную приёмку на виртуальных лампах.

## 8. Приоритет и критерии принятия будущих изменений

**Не терять** эти требования в процессе разработки даже если текущее ПО пока покрывает только ручное сканирование и HA UI.

Порядок:
1. Подтвердить домашний LAB и базовую кнопку/ручной scan.
2. Довести назначения действий, HA UI дерева, результаты скана, подтверждаемое удаление, статус-карточку.
3. Отдельно принять Mode Keeper и Maintenance Mode для реальных совместимых устройств.
4. Привязать описательную электрическую топологию (DIN-реле → Aqara outputs → нагрузки) без опасных команд.
5. **Только после фактического power-on теста поддерживаемых устройств** проектировать исполняемый cascade с безопасным trigger и restore plan.
6. Проверить Startup OFF членов Zigbee group и решить место будущего Light Startup Keeper.

**Критерий продукта:** ввод, замена, обслуживание и восстановление на объекте не должны вынуждать пользователя вручную пересоздавать автоматизации и угадывать состояние реле или ламп.

### Что уже действительно реализовано (по состоянию на 0.1.1)

Экспериментальный MQTT pilot: ручное сканирование, append-only импорт в Supervisor Options, диагностические сущности и базовые Lovelace-карточки, виртуальные HA light test fixtures как отдельный package. **Нет** подтверждённой домашней приёмки, действующего Dispatcher, Mode Keeper, Maintenance, удаления по ссылке с подтверждением, каскада или группового startup Keeper.
