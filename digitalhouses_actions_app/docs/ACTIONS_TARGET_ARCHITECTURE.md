# DigitalHouses Actions App — целевая архитектура v0.3.0

**Статус:** согласованное направление разработки, 26.11.2026.
**Релиз 0.3.0:** первая версия DH Actions для аппаратной приёмки; общие действия не включены. Глобальные профили System Globals содержат независимые CCT и RGB; с 0.3.2 для двухрежимного светильника обязателен явный выбор CCT или RGB.

**Исходная рабочая версия:** DigitalHouses Aqara Switch App v0.2.3.
**Этот документ описывает цель, а не уже реализованные функции.** Рабочий
код, релиз и установку Aqara сохраняем до готовности нового продукта.

## 1. Назначение и границы

Actions — управление исполнительными устройствами дома преимущественно
с физических выключателей, батарейных кнопок и панелей (80–90% сценариев
в типовой установке владельца), а также от датчиков, расписаний и общих
действий. Это не универсальный редактор автоматизаций.

| Идентичность | Целевое значение |
| --- | --- |
| Название | DigitalHouses Actions App |
| Короткое название | DH Actions |
| Product ID, HAOS slug, каталог | `digitalhouses_actions_app` |
| HA entity prefix | `dh_actions_app` |
| Ingress | Actions |
| GHCR | `ghcr.io/digitalhouses/digitalhouses_actions_app` |
| Первый целевой релиз | `digitalhouses_actions_app-v0.3.0` |

Полное переименование выполняется до тиражирования. По [Product Naming
Standard](../../docs/standards/PRODUCT_NAMING_STANDARD.md) новый slug означает
новую установленную сущность Supervisor, а не прозрачное обновление старой.
Исторические теги неизменны. Не требуется перенос старого /data или старых
Supervisor Options; пользователь экспортирует JSON, устанавливает новый App
и импортирует назначения. Проверить совместимость формата экспорта v0.2.3:
не терять параметры и не подменять несовместимые назначения молча.
Старый App и новый App не должны одновременно выполнять те же назначения
или удерживать одни и те же реле. Оформление смены identity, registry, CI,
release, GHCR, telemetry, MQTT Discovery и DH Sync — выполнены при переименовании; аппаратная приёмка предстоит.
Старые ресурсы DH Sync удаляются/заменяются только по согласованной процедуре
вывода старого продукта; соседние панели и продукты не редактируются
без согласования с их владельцем.

### Ответственность продуктов

| Продукт | Ответственность |
| --- | --- |
| Actions | Клавиши, Mode Keeper, датчики, исполнительные устройства, таймеры, расписания, общие действия, применение профилей, журнал, machine events |
| DH Presence | Определение присутствия людей/ухода; может вызвать общее действие Actions |
| DH Climate | Алгоритмы климат-контроля и регулирования; Actions только вызывает поддерживаемые команды |
| Глобальный режим дома / будущий DH Home Mode | Источник Day/Night, расписание режима и ручное переключение |
| Будущий DH Relay | Электротопология, питающие DIN-реле, фазы L1/L2/L3, контроль линий, каскад питания |
| Будущий DH Voice | Подписка на машинные события, тексты, TTS, язык, колонки, очередь и громкость голосовых сообщений |

DIN-реле как топология, привязки к фазам, восстановление питания и каскады
**исключены** из Actions. Исторический `panel_relay` и описание каскада
в field-lessons сохраняются как история, не как требования нового продукта.
Обычная управляемая switch-сущность (розетка/вытяжка) остаётся допустимой целью;
это не делает Actions менеджером питающих линий.
Никаких обязательных зависимостей от будущих приложений, Node-RED, новой
БД или второго брокера. Все функции Actions, не требующие внешнего
источника, работают без него.

## 2. Архитектура

```text
Z2M inventory / actions + HA registry / states + sun.sun + global Day/Night
                     |
   Keys | Motion/Presence | Schedules | Common actions
                     |
     Rules + capability validation + guards + timers + profiles
                     |
          Shared execution engine + state observation
                  /                     \
       Verified Z2M MQTT           Verified HA API
           devices/groups          native entities/services
                  \                     /
         LOG + observed state + transient domain events
```

Ingress — настройка; App — исполнение; HA Dashboard — отображение.
Один существующий Engine, расширяемый по доменам; не вводить отдельные
несогласованные механизмы отправки команд для каждого источника.
Подтверждённые Z2M маршруты для светильников и групп сохраняются.
HA API используется для проверенных нативных сущностей и поддерживаемых
операций остальных доменов; не обходить проверку Z2M маршрута fallback-ом.
Использовать существующие MQTT-клиент, HA registry, подписки и кеш состояния.
Scan на старте, периодически (существующий интервал 60 минут, 0 отключает)
и вручную из Ingress; Scan не выполняет физические записи. Сохранять
отсутствующие, отключённые и переименованные назначения с диагностикой.

## 3. Клавиши и адаптеры оборудования

Одна физическая панель может содержать несколько независимо настраиваемых
клавиш. Тип определяется для каждой клавиши, не для устройства целиком.

| Тип | Управление | Aqara | Actions |
| --- | --- | --- | --- |
| Физическая | Собственное реле, локальная работа | control_relay | **Нет** |
| Логическая | Назначенные сущности | decoupled | Только фактически объявленные/поддерживаемые события |

Батарейная кнопка и панель без встроенного реле — логические, Mode Keeper
не нужен. У физической клавиши нельзя назначать single/double/hold и другие
Actions: её локальное переключение не должно конфликтовать с Engine.
Опциональный таймер выключения физической нагрузки начинается от наблюдаемого
ON её собственного реле, не от события нажатия.

Mode Keeper удерживает заданный режим на поддерживаемых клавишах: физическая
— control_relay (без принудительного изменения состояния реле); логическая —
decoupled и отдельно «Удерживать» ON либо OFF. В Ingress ровно два выбираемых
типа клавиши; поле удержания показывается только у логической проводной
клавиши. Батарейные кнопки логические без поля удержания. Новую логическую
клавишу сохранять только после выбора ON/OFF. Старый decoupled без удержания
и ещё не настроенные клавиши не менять автоматически. Не включать
неиспользуемые выходы автоматически. Для Aqara сохранять проверку capabilities,
координатора, IEEE, совместимого fingerprint и свежего состояния, задержку
восстановления, безопасный Maintenance (локальный режим без изменения питания).
Политика задаётся явно пользователем. Недоступное/неизвестное состояние не
является основанием для слепого включения. Аппаратная приёмка проводных
Aqara отложена до получения выключателей.

Бренд не является фильтром всего приложения. Базовый адаптер принимает
проверенные Z2M Actions, специфический адаптер отвечает за режимы, соответствие
физических клавиш и реле, особенности конкретной модели. Начать с Aqara и
подтверждённых event-only устройств, расширять по фактическим возможностям;
не обещать поддержку произвольных моделей и не менять существующий Zigbee
binding автоматически. Не исполнять события физической клавиши.
Если измеритель мощности есть, показывать W **на уровне устройства**,
не на уровне клавиши; unknown/unavailable = — W, нет измерителя = скрыть
поле. Не вычислять мощность отдельных нагрузок из общей.

## 4. Назначения и домены

Один Action содержит один или несколько адресных назначений, каждое со
своей операцией, параметрами и опциональным таймером; смешанные домены
допустимы. Пример: single — Toggle света, double — ON вытяжки на 30 минут,
triple — Play радио, hold — OFF света и вытяжки + Stop музыки.
Повторение одного события не должно порождать лишние команды.

Инженерный «Тест» у светильника в Entity Picker и редакторе назначения:
одна явная команда ON ↔ OFF через существующий Engine, с проверкой
маршрута и наблюдаемого состояния, без изменения привязок и без эмуляции
нажатия клавиши. LOG: TEST. Отправка не считается подтверждением; повторный
тест блокируется до результата предыдущей команды. Недоступная цель или
глобальный Maintenance блокируют тест. Группа проверяется как одна
подтверждённая групповая сущность, не как индивидуальный ACK каждого участника.

| Домен | Операции (только если поддерживаются конкретной сущностью) |
| --- | --- |
| light | Toggle, ON, OFF; яркость, CCT или RGB, transition |
| switch | Toggle, ON, OFF |
| cover | Toggle, Open, Close, Stop, Position |
| climate | Toggle/ON/OFF если доступно, HVAC mode, temperature |
| media_player | Play/Pause, Play, Pause, Stop, Next/Previous, volume, воспроизведение выбранного медиа |

Для cover Toggle однозначно разрешать из подтверждённого состояния; не
угадывать неизвестное состояние и не обходить защиту. Climate: не изобретать
режимы HVAC, температуры, presets; использовать capabilities и допустимые
границы. ON/OFF/Toggle по заявленным feature flags; Toggle разрешается
из текущего HVAC mode, не из hvac_action. Температура — отдельная команда
для одиночного setpoint, с сохранением единицы HA, проверкой границ и шага;
при смене единицы или режиме, требующем диапазон, команду не отправлять.
Media: только доступные операции; не запускать проигрывание
ради регулирования громкости. Громкость 0–100%, off/standby пропускать.
Выбор медиа через read-only HA media_player/browse_media при заявленных
PLAY_MEDIA и BROWSE_MEDIA; хранить ID, тип и название выбранного элемента.
Воспроизведение только по явному Action. Stop, Next/Previous и Play Media
на этом этапе подтверждают принятие сервиса, а не результат воспроизведения. Никаких произвольных строк HA service или MQTT
topics, пользователь выбирает сущности и операции из каталога.
Сохранять атомарную запись назначений, capability validation, контроль
верификации маршрута, skip offline, общий согласованный Toggle для света
(не инвертировать хаотично разнородную группу), исключение дублирования
участников Zigbee groups. Не считать групповое состояние доказательством
состояния каждого участника.

## 5. Профили и глобальный режим

Единственный владелец глобальных параметров — отдельный будущий модуль
режимов дома. Он пока не реализован. В нём задаются отдельно для Дня и Ночи
яркость, CCT, RGB и громкость. Actions только читает параметры, не
публикует их, не хранит их копии в конфигурации и не показывает ползунки
глобальных значений.

Три режима назначения светильника (независимо от операции ON/OFF/Toggle):
- **ON/OFF**: без параметров, в том числе для обычных светильников.
- **Фиксированные**: вложенный выбор **День / Ночь / Свои**. День и Ночь
  всегда ссылаются на соответствующий глобальный профиль независимо от
  текущего режима дома. Свои — индивидуальные параметры только этой цели.
- **День/Ночь**: брать глобальный профиль текущего режима дома.
  Прежде всего для Motion/Presence, но доступен и для клавиш.
- Для media_player та же модель источника громкости; обычные команды
  воспроизведения без изменения громкости остаются независимыми.
- Параметры и поля UI ограничены capabilities устройства; у простых
  светильников дополнительных настроек нет. Не терять старый JSON.
- Астрономия — отдельный источник расписания.

Внешний модуль выставляет night_mode = on | off (on — Ночь, off — День).
Actions не определяет режим и не пишет этот флаг.
Канонический контракт: [System Globals](../../digitalhouses_system_globals_app/README.md),
разделы 4–5 (System Globals 0.1.5). Actions только подписывается с QoS 1:
- `DigitalHouses/Global/night_mode/state` — retained on/off;
- `DigitalHouses/Global/night_mode/profiles` — retained JSON с обоими
  полными профилями day/night. Поля brightness, color_temp_kelvin,
  rgb_color, volume, transition_seconds и прочие поля §4.
  Незаданные параметры null, ноль валиден. CCT и RGB независимы в глобальном профиле; для двухрежимной цели обязателен явный выбор CCT или RGB, без автоматического переключения.
Не подписываться на команды, не публиковать собственное состояние дома.
Неподдерживаемый или незаданный цвет не передаётся; яркость независима.
CCT ограничивается диапазоном цели. Transition при поддержке ограничен
существующим диапазоном Engine 0–60 сек. Явная brightness=0% означает
отсутствие освещения (OFF); не подменять 1% или обычным ON.
Не преобразовывать RGB↔CCT, не подставлять значения по умолчанию.
Фиксированный day/night доступен независимо от получения state;
current требует оба валидных входа. Порядок начальной доставки не важен.
Изменение profiles само по себе не вызывает автопереход; переход только
по фактической смене state в текущем сеансе. При отсутствии параметров
для данной цели пропуск с записью в LOG.
В назначении сохраняется data.profile = day / night / current, для двухрежимного светильника также data.color_source = cct / rgb,
или индивидуальные поля старого формата; профили не включаются в экспорт.
При отсутствии валидного снимка команды ON с профилем пропускаются,
OFF и независимые назначения работают. Toggle использует общий выбор
направления, OFF не зависит от профиля. При потере MQTT снимок сбрасывается.
LOG профильного ON подтверждает только свежие соответствующие значения яркости и выбранного CCT/RGB; один ON недостаточен. Для Z2M сравниваются фактически отправленные brightness/mired/XY/HS, для HA — атрибуты и активный color_mode. Допуски учитывают округление; отчёт группы не подтверждает каждого участника. Новая команда заменяет ожидание старой, без блокировки управления и дополнительного опроса.

Единый параметр приложения **«Автопереход День/Ночь»** (auto_day_night,
bool, по умолчанию false, в штатной конфигурации HAOS).
Начиная с 0.3.8 доступен в Ingress → Параметры и MQTT switch
`switch.dh_actions_app_auto_day_night`. Оба интерфейса изменяют
одну Supervisor option без рестарта; retained state отражает принятое
значение, команды ON/OFF не retained. Смена флага не применяет текущий
профиль и отменяет устаревшие задания адаптации.
Исполнитель реализован отдельно от формата внешнего сообщения. Начиная
с 0.3.12 глобальная адаптация света не анализирует привязки инициаторов.
Вкладка **Lights** перечисляет светильники из каталога Scan и проверенные
Zigbee-группы. Для каждого явно выбираются два независимых флага:
День/Ночь и Adaptive CCT. Новые и существующие цели по умолчанию не
выбраны; привязки не переписываются. Настройки сохраняются атомарно в
/data/lights.json; существующий импорт/экспорт JSON относится к привязкам.
Для RGB+CCT требуется явный выбор источника цвета. RGB исключает Adaptive.
ON/OFF-only не поддерживает адаптацию; яркость без CCT/RGB поддерживает
День/Ночь. Выбор Lights не ограничивает явные команды Actions.

Day/Night при общем auto_day_night=ON применяется только по реальному
переходу режима к выбранным ON-целям, независимо от инициатора включения.
Используются поддерживаемые параметры глобального профиля. Существующая
адаптация media_player и lifecycle датчиков сохраняются: если активный
владелец-датчик имеет отдельные параметры режима, они применяются к
невыбранной цели; явно выбранный Lights Day/Night определяет параметры
при переходе. OFF по неактивному блоку датчика сохраняет приоритет.

Adaptive CCT независимо от общего переключателя работает каждые 30 минут
только с включёнными CCT-целями. Источник границ — night/day CCT из
System Globals, источник времени — sun.sun (next_rising, next_noon,
next_setting) и часовой пояс HA. Восход/закат соответствуют ночной CCT,
солнечный полдень — дневной, между ними косинусная интерполяция по фазе
светового дня. Зима и лето имеют одинаковые границы. HA сообщает будущие
события: запоминаются подтверждённые события до rollover; при первом
запуске после события отсутствующая прошедшая точка оценивается по
локальному времени следующего дня. Некорректные данные блокируют
солнечную коррекцию. Границы ограничиваются физическим диапазоном CCT.
Adaptive никогда не изменяет яркость/RGB. При обоих флагах и включённом
общем Day/Night ночью действует ночная CCT, днём — солнечная.
Ручная команда не меняет выбор Lights; следующая коррекция выполняется
по установленным флагам. Повторные параметры не отправляются.

Обе функции используют существующую очередь, проверки состояния,
подтверждения и LOG. Повтор/retained/reconnect не создаёт переход
Day/Night; Maintenance блокирует обе функции. Пересечение выбранной
группы и её участников запрещается при сохранении и проверяется повторно
при исполнении.
Zigbee group обрабатывается только когда каждый участник подтверждён
как online/ON, без незавершённых команд. Если сведений недостаточно —
пропуск; HA groups без проверяемого состава также пропускаются.
Один групповой вызов исключает повторную отправку его участникам.
Z2M отправляет только параметры, без state=ON (явные 0% — OFF). Для HA native светильников
сначала читать live state, затем штатный light.turn_on с параметрами;
HA не имеет атомарного условного сервиса, поэтому одновременное внешнее
выключение между проверкой и вызовом остаётся возможной гонкой.
В LOG отражать пропуски и факт принятия световой команды, не выдавать
его за подтверждение яркости/цвета. Для media volume остаётся
подтверждение по наблюдаемой громкости.
Для Motion/Presence с 0.3.10 каждое назначение содержит два одинаковых блока modes.day и modes.night: enabled, data (ON/OFF, ссылка на глобальный профиль соответствующего режима или собственные параметры), необязательный off_delay_seconds. Старые записи с data/when/night_data читаются без изменения файла, в Ingress отображаются в двух блоках и преобразуются при сохранении. Ранее выбранные глобальные ссылки сохраняются. При неизвестном режиме зависимое от режима включение блокируется, независимые одинаковые блоки работают. При реальном переходе режима с auto_day_night включённым для эксклюзивно принадлежащей активному датчику ON-цели выбирается новый режим, включая длительность таймера; если новый блок неактивен — OFF, если активен — применяются его параметры, кроме явно выбранного Lights Day/Night. Уже начатый таймер отсутствия не сбрасывается. При выключенном auto_day_night сохраняется режим включения. Ручное управление, пересечения, неизвестное состояние и устаревший токен блокируют адаптацию; выключенные цели не включаются при переходе режима.
Общий переключатель Day/Night сохранён; per-light флаги находятся в Lights. Motion/Presence сохраняет собственные блоки режимов и таймеры.
Глобальные расписания Day/Night и TTS не входят в Actions.
Старую автоматизацию громкости отключать только после осознанного перехода
на управление Actions, чтобы избежать двух владельцев одного параметра.

## 6. Motion / Presence / Lux и таймеры

DEV: реализованы каталог HA motion/occupancy/presence, сопоставление Lux
по одному device_id и только с device_class=illuminance и unit=lx,
редактор и сохранение/импорт/экспорт в общем bindings.json schema=1.
Строка binary_sensor.* хранит enabled, assignments и при наличии
Lux — lux_entity_id, lux_threshold. Назначения light/switch используют
явный ON, прежние параметры профиля и опциональный off_delay_seconds.
Порог 0 блокирует автоматический ON. В чистой функции проверки
Lux предел давности 15 минут (консервативное начальное решение,
уточнить по реальным датчикам).
DEV: исполнитель датчиков подключён. Read-only подписка HA state_changed
с baseline и heartbeat, одна общая очередь Engine. Только OFF→ON источника
с валидным Lux и наблюдаемым OFF цели разрешает ON. ON при старте,
unknown/unavailable→ON и уже включённая цель не создают команд.
Владелец — подтверждённое включение от конкретного датчика. При наличии
нескольких датчиков на цель авто-OFF только после отсутствия у всех.
Ручное действие через Actions отменяет владение и ожидающие задания;
наблюдаемое внешнее изменение состояния/параметров также отменяет его.
При одновременных внешних командах нельзя гарантировать атрибуцию
каждого HA события; после неоднозначного изменения таймер пропускается.
Активный подтверждённый владелец динамического профиля разрешает
автопереход при наличии ручных фиксированных назначений. Подтверждённое
совпадение новых параметров сохраняет таймер; несовпадение отменяет его.
Снимок владения и deadline сохраняются в /data/sensor_timers.json;
восстановление только после совпадения наблюдаемых состояния, параметров,
last_changed и конфигурации, без повторного ON. Изменение baseline
отсутствия начинает новый отсчёт, а не воспроизводит старый OFF.
Группы Zigbee2MQTT поддерживаются с проверяемым составом: каждому члену
соответствует ровно одна существующая индивидуальная HA-сущность и
проверенный Z2M маршрут. Одно multicast ON только если все члены OFF
по HA и свежим Z2M данным, online и без незавершённых команд.
Смешанное состояние группы не изменять. Подтверждение групповой
сущности не даёт владения: нужны наблюдаемые ON всех членов.
Сохранять индивидуальные сигнатуры и точный состав группы вместе с
deadline. OFF multicast разрешён только при совпадении всех сигнатур,
свежем ON каждого члена и подтверждённом отсутствии у всех связанных
датчиков. Дополнительно перечитать HA states перед отправкой.
Ручное управление любым членом отменяет групповой таймер целиком.
Пересекающиеся разные цели датчиков (группа/член, две группы) не
исполнять до устранения неоднозначности; одинаковая группа у нескольких
датчиков разрешена. Не заменять групповую команду fan-out.
HA groups без подтверждённого индивидуального маршрута пока не
предлагать; существующие назначения сохранять с предупреждением. Реальные тесты Z2M/HA и
приёмка подписки остаются. Нативная HA команда и проверка не атомарны;
одновременное внешнее управление остаётся возможной гонкой.
Ingress: все таймеры (датчики, логические клавиши, физические реле)
редактируются одним полем MM:SS; остаток и заданная длительность
отображаются в том же формате. Начальное значение новых назначений
датчика 00:00 — немедленный OFF после отсутствия. Пустое поле (кнопка ×)
отключает таймер; существующее отсутствие длительности не заменяется нулём.
Для таймеров клавиш и реле минимум 00:01. Максимум 1440:00.
JSON хранит длительность целым числом секунд без изменения схемы.

DEV: таймеры клавиш и физических реле реализованы. Для логического
назначения light/switch ON или Toggle опциональный off_delay_seconds
(1–86400, отсутствие поля отключает таймер). Запускается после
наблюдаемого OFF→ON, инициированного этим Action. Уже включённая цель
не присваивается таймеру повторной ON-командой; новое ручное действие
отменяет прежний таймер. OFF использует существующий Engine и проверку
владения, состояние и параметры, включая состав группы. Дедлайны
логических клавиш сохраняются вместе с таймерами датчиков в
/data/sensor_timers.json. Никаких таймеров на Hold ON/OFF логической
клавиши, cover, climate, media_player. Смена назначения, его отключение
и Maintenance отменяют соответствующее владение.
Физическая клавиша: relay_timers = {channel: seconds} в строке switch,
только явно выбранный control_relay. Таймер не создаёт Action,
наблюдает свежие per-channel mode/relay отчёты, требует online,
подтверждённые coordinator/IEEE/fingerprint и writable relay.
OFF публикуется единожды на точный state_* через ту же очередь;
логические реле не затрагиваются. Наблюдаемый OFF, изменение режима,
политики, недоступность или смена identity аннулируют старое задание.
При рестарте/MQTT reconnect нет надёжного времени предыдущего физического
OFF→ON: не воспроизводить старый deadline вслепую. После первого свежего
подтверждённого ON начать полный настроенный интервал заново. Это
консервативное исключение из восстановления точного deadline, требуется
согласование после испытаний. Нативное локальное переключение работает
без Actions. Таймер не является аппаратной защитой нагрузки.
System Globals readiness и натурная приёмка остаются открытыми.

Выбирать совместимые датчики независимо от производителя. Учитывать
реальные классы/возможности motion, occupancy/presence, illuminance.
Lux поле показывать только если датчик действительно предоставляет
освещённость в lx; не выдавать raw illuminance/неизвестную единицу за lux.
При наличии Lux пользователь задаёт числовой порог (например 70 lx или
50000 lx); отдельный флаг использования Lux не нужен. Автоматический ON
только при lux < threshold; 0 не разрешает включение, 50000 — высокий,
но не безусловный порог. Нет Lux у датчика — нет условия. Есть порог,
но измерение неизвестно/недоступно/неактуально — автоматический ON пропустить.
Проверять освещённость только на входе, не выключать свет из-за повышения
Lux от собственного светильника. Ручное управление имеет приоритет.

Авто-OFF — независимая опция, по умолчанию не включать:
- клавиша/физическое реле: отсчёт от включения (например вытяжка 30 мин);
- motion/presence: отсчёт от подтверждённого отсутствия, повторное
  обнаружение отменяет таймер; пока присутствие есть, авто-OFF не срабатывает;
- явный OFF/Stop отменяет соответствующий таймер; ручное включение не
  должно быть неожиданно отменено старым таймером чужого назначения.
Не отсчитывать отсутствие от unavailable. Согласовывать несколько
назначений одной цели; защищать ручное состояние, не запускать циклы.
Сохранять активные дедлайны для безопасного восстановления после рестарта
(в том числе вытяжки), проверять актуальность цели и принадлежность таймера
прежде чем отправлять просроченную команду. Правила разрешения коллизий и
длительность ручного приоритета уточнить до реализации; не добавлять
сложный универсальный DSL.

## 7. Расписания и защитные условия

DEV: точечные ежедневные расписания реализованы в разделе Ingress
«Расписания» (создание, изменение, отключение, удаление). Один логический
ID schedule.* (не HA entity), name, enabled, trigger и assignments
в общем JSON schema=1. trigger: {kind: time, time: HH:MM} либо
{kind: sunrise|sunset, offset_minutes: signed integer -720..720}.
Только явные операции поддерживаемых Light/Switch/Cover/Climate/Media,
без Toggle, Play/Pause, Next/Previous, relative brightness step и
цепочек Auto-OFF. Используется существующий Entity Picker и Engine;
световые/звуковые параметры и профили из System Globals без дублирования.
Датчики окна из всех расписаний (включая отключённые) объединяются
с защитами клавиш для той же шторы. Состояние, маршрут, конфигурация
и Maintenance повторно проверяются перед отправкой; групповой Z2M
маршрут требует подтверждённых доступных участников.

Часовой пояс читается из HA, используется ZoneInfo; образ включает tzdata.
DST: при повторяющемся локальном времени исполнить в первом fold,
несуществующее время пропустить. Солнечные события — next_rising /
next_setting из sun.sun. До смены прогнозного события держать его
подтверждённый момент в памяти, после rollover сохранять для
положительных смещений (не вычислять прошлый рассвет/закат по догадке).
Таймзона неизвестна, sun.sun недоступен или нет подтверждённого
солнечного момента — соответствующее расписание не исполнять.
Только пересечение due в текущем сеансе (окно тика до 10 с, срок
действия задания 30 с), один раз на occurrence. При старте, reconnect,
изменении конфигурации/часового пояса — baseline без replay для обычных
расписаний (catch_up отсутствует или false).
Если прошлое солнечное событие уже не известно после перезапуска,
положительное смещение от него также пропускается.
Точечные команды без catch_up не догонять после простоя.
Согласовано: отдельных интервальных расписаний не создавать. Вместо
них опциональный catch_up: true (по умолчанию false) в строке schedule;
Ingress: «Выполнять пропущенное при перезапуске HAOS».
Компенсация только явных Light/Switch ON/OFF, без cover, climate и
media_player. Штатное точечное расписание с catch_up также ждёт
релевантной готовности. Потреблять живой non-retained lease
DigitalHouses/digitalhouses_system_globals_app/readiness/lease
(контракт System Globals main c5a8f7c: период 5 с, TTL 20 с),
availability и сброс при MQTT/HA disconnect. Не доверять retained on.
Для HA-native нужны mqtt_ready + ha_ready, для подтверждённых Z2M
маршрутов и MQTT-целей — также zigbee_ready (консервативно, MQTT
switch не всегда позволяет доказать принадлежность к Z2M).
Одна небольшая атомарная история /data/schedule_history.json, контрольная
точка для каждой из двух групп готовности каждые 5 с и перед
постановкой очередного события в очередь. Хранить подтверждённый
часовой пояс, revision всех расписаний и маршрутов, известные солнечные
моменты. После потери готовности и нового запуска проверить период
до 24 ч. Для каждой цели выбрать последнее событие, включая расписания
без catch_up; более позднее событие без компенсации отменяет старое.
Равновременный конфликт, неизвестные солнечные данные, смена
конфигурации/часового пояса, неоднозначное пересечение групп, отсутствие
проверенного маршрута/состояния — пропустить, не угадывать. При первой
установке и Maintenance — baseline. При восстановлении уже требуемый
ON/OFF не отправлять, для Z2M группы проверять каждого участника.
Восстановление — однократная постановка в общий Engine, отдельная
запись LOG; никакого непрерывного принуждения и повторных попыток.
Контрольная точка фиксируется до постановки в очередь: при сбое между
записью и отправкой возможно пропустить действие, но не воспроизвести
его повторно. Отдельный offline target не считается простоями HAOS;
не обещать физическое исполнение недоступной цели. Нативные тесты HA и Z2M
по-прежнему обязательны перед релизом.


Универсальный источник: локальное время, рассвет, закат, signed offset
в минутах, время и timezone из HA. Учитывать переход суток и timezone.
Пример: закат -15 min ON наружного света, рассвет +20 min OFF; для штор
рассвет +30 min Open, закат Close; обычное расписание 08:00 Open.
Использовать авторитетные астрономические данные HA (sun.sun); учитывать
следующие события и пересчёт на границах суток. Не вычислять по догадке
при отсутствии исходных данных. Для явно заданного интервала наружного
света предусмотреть восстановление требуемого состояния после перезапуска;
не воспроизводить пропущенные команды ворот/штор вслепую.

Опциональная блокировка движения cover по одному или нескольким
оконным binary_sensor (window/door/opening по подтверждённым capabilities):
если хотя бы одно окно открыто, состояние неизвестно или датчик недоступен,
не разрешать Open/Close/Position/движущий Toggle. Применять ко всем
командам приложения, в том числе от клавиши, расписания, общего действия.
Stop не блокируется. На этапе клавиш датчики сохраняются в назначении cover,
при исполнении используется объединение защит всех сохранённых назначений
этой цели, в том числе отключённых и отсутствующих клавиш. Toggle в движении
не угадывает направление; пользователь может назначить явный Stop.
Не возобновлять пропущенное движение при закрытии
окна автоматически. Штатная аппаратная защита ворот/гаражей обязательна;
программная проверка — дополнение, не замена. Не обходить защиту и не
выдавать состояние команды за подтверждение физического движения.

## 9. Ingress, хранение и наблюдаемость

Стиль Network App, компактная полноширинная компоновка, основной экран
«Клавиши», дополнительно «Датчики», «Расписания», «Общие действия»,
«Профили». В шапке Scan, экспорт, импорт, JSON, LOG. На основном экране
устройство → типы клавиш → краткие action/target summaries; вся строка открывает
настройку. Z2M friendly_name — отличающееся имя устройства HA (name_by_user/name). Физические клавиши без Actions. Мощность на уровне устройства.
Отдельные пиктограммы доменов, групп, текущего состояния и проблем.
Для каждой управляемой сущности в списке устройств обязательно отображать
полный entity_id (включая домен) — Friendly Name из HA, например
climate.thermostat_living_room - Термостат Зал. Правило едино для всех
текущих и будущих доменов. Если имя отсутствует или совпадает с entity_id,
показывать полный entity_id без дублирования; отсутствующая сущность
сохраняет полный ID и предупреждение. Не сокращать ID до object_id.
Редактор показывает только параметры выбранного сценария и capabilities;
ON/OFF без развёрнутых настроек яркости/цвета. Единственное явное Save,
атомарное применение без перезапуска. Нет управляющих YAML в HAOS.

Entity Picker по образцу DH Climate
(`dh_climate_app/src/dh_climate_app/web/entity_picker.js`):
поиск по имени/entity_id/комнате/устройству; фильтры домена, комнаты,
интеграции, доступности; предвыбор комнаты устройства; множественный
выбор, состояние, место использования, сохранение отсутствующих и
выбранных за пределами фильтра сущностей. Подбор датчиков — классы и
единицы; подбор целей — совместимые домены. Выбор редактирует форму,
не вызывает сервис. Реализация в коде Actions, без изменения DH Climate.

Один локальный конфигурационный JSON, схема с версией, атомарный экспорт/
импорт, просмотр JSON, явная валидация, без секретов. Системные параметры
остаются в Supervisor Options. Не смешивать пользовательские назначения
с обнаруженной топологией/временными состояниями и журналом.
Сохранить рабочую механику v0.2.3: LOG закрыт по умолчанию, справа ~50%,
одна строка на исходное событие с несколькими целями, локальное время HA,
500 записей / 24 часа в SQLite /data/actions_log.sqlite3, инкрементальная выдача, кнопка «Выгрузить» (JSON), сохранение при рестарте без повторного выполнения незавершённых команд. При ошибке SQLite — RAM и явное предупреждение. Подсветка
нажатий и состояния. ✓ — отправлено/сервис принял; ✓✓ — наблюдаемое
соответствующее состояние; ⚠ — пропуск/нет подтверждения с причиной.
Не считать Z2M optimistic state или HA service acceptance физическим ACK.
Для операций без наблюдаемого результата не рисовать ✓✓ по умолчанию.
Для параметров (яркость, CCT, громкость, position, temperature) подтверждать
соответствующее значение, а не только ON. Существующий таймаут 90 сек —
базовый; для профильных параметров добавляется заданный transition; не выдавать завершение длительного движения cover преждевременно.

## 10. Машинные события и DH Voice

Actions публикует машинные факты; не содержит настроек голосовых текстов,
TTS, выбора колонок для уведомлений, локализации или маршрутизации
голосовых сообщений. DH Voice (отдельный будущий продукт) подписывается
и сам решает, что, где и когда озвучить. Управление музыкой/громкостью
по клавишам/профилям остаётся в Actions, голосовая доставка — в Voice.

Предложенная доменная маршрутизация:
```text
DigitalHouses/Global/events/light
DigitalHouses/Global/events/switch
DigitalHouses/Global/events/cover
DigitalHouses/Global/events/climate
DigitalHouses/Global/events/media_player
```
system и события иных продуктов — дальнейшее отдельное согласование.
QoS 1, retain=false. Не воспроизводить историю при старте, дедуплицировать
QoS1 повторную доставку по стабильному ID события. State отдельно от Event.
Публиковать факт только после наблюдаемого перехода/изменения; различать
отправленную команду и полученное состояние. Не заявлять о физическом
подтверждении при optimistic state. Не публиковать фиктивные transitions
на стартовом снимке, retained replay, reconnect или повторном неизменном
отчёте. Предпочтительный порядок: авторитетный state -> retained state
(если применяется) -> transient event.

Согласовать реализацию с существующим
[Events & Notifications Standard](../../docs/standards/EVENTS_AND_NOTIFICATIONS_STANDARD.md)
и [Contract Data Policy](../../docs/standards/CONTRACT_DATA_POLICY.md):
отдельная machine schema для каждого event_type, MQTT Event Discovery
там, где применимо, без универсального notification envelope.
Пример целевого контракта climate_state_changed (проект, не выпущенный API):
```json
{
  "schema_version": 1,
  "event_type": "climate_state_changed",
  "event_id": "unique-occurrence-id",
  "source": "digitalhouses_actions_app",
  "entity_id": "climate.bedroom",
  "previous_state": "heat",
  "state": "off",
  "trigger": "aqara_bedroom.single_left",
  "observed_at": "2026-11-26T00:15:00+05:00"
}
```
Доменные схемы определяют обязательность полей (например trigger только
когда причинная связь действительно установлена); не подставлять неизвестные
данные. Для cover различать opening/open/closing/closed. Voice может
озвучить climate.bedroom -> off как «Климат-контроль в спальне выключен»,
но этот текст отсутствует в MQTT producer payload.
Не вводить второй локализованный notification event, адаптер или
обязательную подписку Voice. Не менять общий стандарт и чужие продукты
в рамках этой разработки. Межпродуктовое принятие доменных топиков и
правила единственного producer при пересечении Actions/Climate/Voice —
отдельное согласование до стабилизации контракта DH Events.

## 11. DH Sync, delivery и тестирование

Следовать [DH Sync](../../docs/standards/DH_SYNC_DEVELOPER_STANDARD.md),
[Unified Product Status Card](../../docs/standards/UNIFIED_PRODUCT_STATUS_CARD_STANDARD.md),
[Operation UI](../../docs/standards/OPERATION_UI_STANDARD.md),
[Manual Refresh](../../docs/standards/MANUAL_REFRESH_STANDARD.md) и действующим
release/telemetry правилам. Новый ID в /sync, QoS1 retained на каждом
connect/reconnect; schema, product_id, type, version, repository, product_path.
Canonical view в dashboards/ru, пакеты по действующему стандарту;
панели принадлежат DH Sync. Телеметрия Apps остаётся opt-in.
Никаких изменений чужого кода ради интеграции без отдельного задания.

### Предлагаемый порядок реализации (не отдельные обязательные релизы)

1. Закрепить модель конфигурации и identity; сохранить рабочий Engine,
   тесты v0.2.3, JSON import/export и LOG.
2. Клавиши physical/logical, адаптер Aqara, общий Entity Picker,
   пять доменов и смешанные назначения.
3. Датчики, lux, опциональные таймеры, профиль Day/Night и адаптация
   включённых светильников / активных колонок.
4. Расписания, защитные условия cover, общие действия и OFF reconciliation.
5. Доменные Events, документация, канонический dashboard/Sync,
   registry/CI/immutable delivery; выпустить Actions после приёмки.

Acceptance: существующие одиночные и групповые light toggles и JSON v0.2.3
не деградируют; нет Actions для physical; смешанный hold выключает свет,
вытяжку и останавливает медиа; Motion/Presence с Lux и без; таймеры
опциональны и сохраняются безопасно; Day/Night не включает выключенное;
блокировка окна при open/unknown/unavailable действует на все источники;
астрономия с signed offset, сменой суток, restart; дедупликация групп и
исключения all lights; ✓✓ только по наблюдаемому результату; QoS1 non-retained
events без TTS; стандартные CI/repository checks и smoke test на HAOS.
Проводные Mode Keeper, фактическая работа cover/climate/media, реальное
освещение и аппаратная безопасность требуют натурной проверки.

### Не входит в текущую реализацию

DH Relay / каскады / фазы / питающая топология; DH Voice и общий глобальный
Event Bus стандарт для остальных продуктов; перенос глобального night_mode
пакета; переписывание DH Climate, DH Presence, DH Sync. Не разрабатывать
автоматическую миграцию установки Aqara. Точные границы профилей,
legacy fixed parameters, разрешение конфликтов/ручного приоритета и
окончательные event/command schemas уточняются в рамках реализации;
не считать открытые технические решения уже согласованными API.
