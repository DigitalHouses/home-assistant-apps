# DigitalHouses System Globals

Статус: экспериментальное приложение; автоматическое обнаружение Zigbee2MQTT с 0.1.1. Дата: 2026-11-26.

## 1. Назначение и идентичность

Единый авторитетный поставщик системных режимов, профилей и флагов готовности. Не управляет исполнительными устройствами и не вычисляет присутствие жильцов.

- Согласованное название: DigitalHouses System Globals; UI: DH System Globals.
- Канонический product ID, каталог и будущий HAOS slug: `digitalhouses_system_globals_app`.
- HA entity prefix: `dh_system_globals_app`. Тип: app (haos_addon).
- Публичный межпродуктовый namespace: `DigitalHouses/Global/`.
- Служебный namespace продукта: `DigitalHouses/digitalhouses_system_globals_app/`.
- Иконка: mdi:state-machine.
- Нормативные документы: [стандарты репозитория](../docs/standards/), включая Naming, Contract Data, Events, DH Sync, Operation UI, Manual Refresh, Unified Status Card, Release, Telemetry.

Кандидат 0.1.0 зарегистрирован с канонической идентичностью; выпуск только после всех обязательных проверок. Включение обязательной телеметрии для публичного выпуска подчинено legal gate репозитория.

## 2. Архитектура

Четыре небольших модуля: System Modes, System Profiles, System Gates, System Lifecycle. Один процесс App, одно постоянное хранилище /data, один обработчик изменений. Ingress (администратор) и HA Dashboard (владелец) работают с одними данными. Ingress обращается к внутреннему API; HA использует MQTT Discovery, включая управляемые сущности. Никаких дублирующих HA Helpers или HA-автоматизаций для бизнес-логики. Команды из голоса/HA/MQTT/Ingress равноправны. App не требует HA Core для Modes/Profiles; отказ HA-диагностики влияет только на соответствующий Gate. Полная остановка HAOS останавливает App; после запуска восстановить состояние.

Никаких прямых вызовов светильников, колонок, исполнительных устройств. DH Electrica, Voice и прочие потребители действуют самостоятельно. DH Presence существует отдельно; его код, конфигурацию, вычисление we_at_home и контракт не изменять.

## 3. System Modes

Активный night_mode: on = ночь, off = день. Настройки auto_switch, night_start, night_end (HH:MM в локальном часовом поясе). Расписание — две команды на границах суток, а не непрерывное принуждение. Ручная/голосовая команда не выключает автоматику; сохраняется до следующей команды или границы. Автоматика off: только ручные команды. Равные времена невалидны для включенной автоматики. При редактировании расписания или включении auto_switch не отменять ручной выбор немедленно; применить будущие границы. При перезапуске восстановить сохраненный режим и применить последнюю реально пропущенную границу после сохраненного момента обработки, не воспроизводить цепочку старых команд. Хранить состояние, конфигурацию и отметку обработанной границы атомарно; учитывать смену суток и часового пояса. При первичном запуске без конфигурации не выдумывать режим, профили или время; администратор явно задает исходные значения. Часовой пояс — явная настройка либо подтвержденная системная зона, не зависимость от HA API.

## 4. System Profiles

Публиковать оба профиля одновременно. Профили доступны независимо от текущего режима. Параметры для каждого day/night:
- brightness: целое 0..100, %.
- color_mode: `cct` | `rgb` — независимый выбор для каждого профиля day/night.
- color_temp_kelvin: целое 2000..6000, K (диапазон старого пакета; ограничения конкретного устройства — у потребителя).
- rgb_color: JSON-массив `[R, G, B]`, ровно три целых числа 0..255.
- volume: целое 0..100, %; преобразование в 0..1 на стороне потребителя при необходимости.
- display_brightness, indicator_brightness: целые 0..100, %.
- transition_seconds: неотрицательное конечное число, секунды.
- voice_notifications_enabled, noncritical_sound_notifications_enabled: boolean. Критические уведомления не блокируются этим профилем.

Не использовать defaults: незаданные значения явно null; потребитель не выдумывает значения. 0 — валидное значение, не отсутствие. Изменение одного параметра атомарно сохраняет остальные. Потребитель может использовать текущий профиль, фиксированный day/night либо собственные параметры. Изменение профиля не является событием изменения режима. `color_temp_kelvin` и `rgb_color` строго взаимоисключающие: при `color_mode=cct` заполнен только color_temp_kelvin, rgb_color=null; при `color_mode=rgb` заполнен только rgb_color, color_temp_kelvin=null. Оба ненулевых значения в одном профиле недопустимы: явно противоречивую команду или импорт отклонить целиком. При смене color_mode атомарно задать валидное значение нового режима и очистить противоположное поле (null); старое неактивное значение не хранить. В незаданном профиле допустимы color_mode=null и оба цвета=null; не публиковать настроенный color_mode без соответствующего валидного значения. Не выполнять автоматическое преобразование RGB↔CCT и не подставлять цвет по умолчанию. Яркость и остальные параметры независимы. При изменении режима или цвета валидировать весь обновляемый профиль атомарно. Ограничения возможностей светильника обрабатывает потребитель; неподдерживаемый цвет не отправлять, яркость применять независимо. Другие color_mode не добавлять без отдельного требования.

## 5. MQTT: Modes / Profiles

Все топики чувствительны к регистру. QoS 1; state/discovery retained, команды и события non-retained. Команды с retain запрещены. Только App публикует авторитетные глобальные состояния.

| Топик | Payload | Retain |
| --- | --- | --- |
| DigitalHouses/Global/night_mode/state | on/off | true |
| DigitalHouses/Global/night_mode/set | on/off | false |
| DigitalHouses/Global/night_mode/profiles | JSON: day, night (brightness, color_mode, color_temp_kelvin, rgb_color и остальные параметры §4) | true |
| DigitalHouses/Global/night_mode/event | JSON: night_mode_on/off | false |
| DigitalHouses/digitalhouses_system_globals_app/config/state | JSON: auto_switch, night_start, night_end, timezone | true |
| DigitalHouses/digitalhouses_system_globals_app/config/set | JSON partial update | false |
| DigitalHouses/digitalhouses_system_globals_app/profiles/set | JSON partial update day/night | false |

Пример световой части payload `/profiles` (условные значения, не defaults; остальные поля §4 также входят в полный payload):

```json
{
  "day": {"brightness": 100, "color_mode": "cct", "color_temp_kelvin": 4000, "rgb_color": null},
  "night": {"brightness": 20, "color_mode": "rgb", "color_temp_kelvin": null, "rgb_color": [255, 80, 0]}
}
```

Тот же формат используется для частичного обновления `/profiles/set`, например `{"night":{"color_mode":"rgb","rgb_color":[255,80,0]}}`. Изменение цвета и режима цвета не генерирует night_mode_on/off.

Состояние и профили публиковать после сохранения, при подключении/переподключении MQTT и при необходимости HA discovery. Не воспроизводить Event при republish/reconnect. Если режима нет, не публиковать фиктивный off; очистить недостоверное retained состояние. Для MQTT Discovery редактируемых полей обеспечить совместимость с нативными scalar command payload через служебные адаптеры команд, не создавая второго источника истины. Точные служебные entity-топики фиксируются при реализации.

Пример event: `{"schema_version":1,"event_type":"night_mode_on","observed_at":"2026-11-26T23:00:00+05:00"}`. Второй тип night_mode_off. Только фактический переход; сначала сохранить, затем опубликовать state, затем event. При недоступном MQTT не проигрывать задним числом устаревшие уведомления. QoS 1 допускает повторную доставку; потребитель не должен повторно исполнять опасные команды на основании доставки.

## 6. System Gates

Цель: не допускать лавины ложных событий unavailable/unknown при старте и перезапуске HA, MQTT, Z2M. Старый пакет ставил gate через 30 секунд после HA start; проверка Zigbee была отключена. Новый Gate динамический и основан на подтверждении готовности, не на одной задержке.

Состояния каждого источника: gate on/off, диагностическая причина (starting, disconnected, probing, ready, failed и т.п.). Неопределенность закрывает gate, но не считается доказанной аварией. После старта App, нового MQTT-сеанса или потери компонента закрыть соответствующие gates; открыть после проверок текущего сеанса. Источник конфигурации обязательных компонентов — настройки администратора; MQTT всегда обязателен, HA и Z2M включаются в общий gate явно. Для типового HA+Z2M все три обязательны. Потребитель использует только релевантные ему gates.

### 6.1 MQTT

После CONNACK и SUBACK выполнить короткий non-retained roundtrip на собственном служебном топике с уникальным nonce; получить собственный актуальный ответ и PUBACK. При разрыве соединения, неуспехе или таймауте gate off локально. Не считать старый retained on доказательством здоровья. Повторять контроль с разумным интервалом. Включить LWT offline для доступности App. При восстановлении сначала объявить закрытые gates, выполнить проверки, затем публиковать готовность. Потребитель закрывает собственный gate при потере MQTT или доступности производителя; не использует кэш как свежий факт. Для защиты от устаревшего retained on после рестарта брокера — проверка свежести служебного heartbeat/сеанса с ограниченным сроком жизни; точные интервалы проверить тестами. Никакой команды на исполнительные устройства для проверки.

### 6.2 Home Assistant

Слушать настроенный birth/will (обычно homeassistant/status online/offline). online — повод проверить, не доказательство готовности. Использовать обнаруживаемый диагностический MQTT sensor с non-retained уникальным nonce; после подтвержденной публикации проверить через локальный HA API, что Core в RUNNING и сущность действительно получила этот nonce в текущем сеансе (не unknown/unavailable). При недоступности API/интеграции gate off; повторить проверку после восстановления, без HA-автоматизаций. HA API нужен только этому модулю, не Modes/Profiles. Отслеживать HA offline, разрыв наблюдения и повторять probe с ограниченной частотой. Не ждать всех HA entities и не считать readiness доказательством валидности всех интеграций. Проверку фактических потребляемых сущностей выполняет потребитель.

### 6.3 Zigbee2MQTT

Автоматически обнаруживать все экземпляры Zigbee2MQTT в подключённом MQTT-брокере по топикам */bridge/state, */bridge/info, */bridge/devices с произвольной глубиной префикса. Подписка # с фильтрацией до очереди; чужие топики не обрабатываются. Для каждого экземпляра независимые корреляция и TTL. Zigbee Ready = on только при наличии хотя бы одного обнаруженного экземпляра и свежем подтверждении каждого; offline, новый неподтвержденный экземпляр или истечение TTL закрывает gate. Удаление экземпляра — очистка его retained discovery-топиков. Список обнаруженных экземпляров виден в Ingress. После online/reconnect проверить bridge/info, bridge/devices (валидный inventory, пустой список допустим для пустой сети) и живой запрос bridge/request/health_check с ответом status=ok и data.healthy=true в текущем сеансе. Старые retained info/devices сами по себе не открывают gate. Подписаться до запроса; использовать корреляцию transaction там, где подтверждена поддержка выбранной версии, не принимать старые ответы. После проверки допускается короткий настраиваемый период стабилизации только если реальные тесты покажут необходимость. Не ждать все устройства: спящие/выключенные устройства не блокируют дом. Не обещать, что вся телеметрия каждого устройства актуальна; зависимые действия требуют валидного наблюдаемого состояния конкретной цели.

### 6.4 Потребители

На закрытом gate подавлять производные уведомления от переходных состояний релевантной подсистемы, не подавлять событие о ее собственной недоступности. После открытия — синхронизация baseline без генерации ложных arrival/departure/on/off событий. Unknown/unavailable не эквивалентны off. Реальные отдельные неисправности при готовом источнике должны оставаться видимыми. Gate не является разрешением работы всего дома: автономные назначения Electrica, расписание Night Mode и другие независимые функции продолжаются. Потребители с опасными действиями проверяют актуальность собственных данных. Не менять чужой код в рамках этого продукта.

### 6.5 Публичные топики

Префикс DigitalHouses/Global/:
- mqtt_ready/state, ha_ready/state, zigbee_ready/state, system_ready/state: on/off, QoS 1, retained.
- system_ready/event: JSON, QoS 1, non-retained; event_type system_ready_on/off, schema_version, observed_at, reason при необходимости.
- События отказа/восстановления компонентов — отдельные типы machine event по стандарту, не блокируются собственным gate.

Gate неуправляемый: никаких /set для этих состояний. Диагностические причины, доступность производителя и свежесть сеанса — служебный контракт App; при реализации зафиксировать единый механизм heartbeat/lease и тесты разрыва. Не публиковать лишние глобальные копии тех же состояний.

## 7. System Lifecycle

Фиксировать наблюдаемые старт/остановку HA Core, время работы, простой, штатность завершения только когда достоверно подтверждена. Потеря MQTT или API сама по себе не доказательство shutdown. Без подтверждения причины записывать unknown; не выдумывать время остановки/простоя. Event Discovery: ha_started, ha_stopped (подтвержденное штатное), ha_unexpected_shutdown (только при доказательстве), отдельные события потери/восстановления связи. Машинные события без локализованных сообщений, уведомления — локальные потребители. Название дома можно хранить в общей конфигурации по необходимости, не дублировать существующий site-id. История через Recorder; не связывать функциональность приложения с Recorder.

## 8. UI и интеграции

Ingress: Modes/Profiles, Gates, Lifecycle/LOG; стандартная шапка и диагностика, экспорт/импорт конфигурации по канону. HA Dashboard для владельца: стандартная статусная карточка, переключение режима и автоматики, расписание, редактирование профилей, текущие параметры, история режима, доступные статусы готовности. Для каждого day/night профиля в обоих интерфейсах выбирать CCT/RGB; отображать и редактировать исключительно соответствующий параметр (температура в K или RGB color picker/эквивалентный редактор трех каналов); смену режима сохранять вместе с новым значением и очисткой противоположного поля. Яркость доступна в обоих режимах. Системная диагностика администратора отдельно от пользовательской страницы. MQTT Discovery и DH Sync: /sync, dashboards/ru, packages/common для Recorder, packages/locales/ru для опциональных уведомлений, согласно актуальному стандарту. Голосовой интерфейс через MQTT switch ночного режима. Не вводить обязательную зависимость от уведомлений, HA или голосового сервиса. Телеметрия App — явное принятие условий при первоначальной настройке по текущему общему стандарту; обязательный публичный rollout остаётся под legal gate.

## 9. Миграция

Источники требований: предоставленные владельцем legacy night_mode_global_package.yaml, homeassistant_start_stop_global_package.yaml, we_at_home_package.yaml и Lovelace View nightmode. Они являются исходными материалами, не новым исполняемым кодом. Presence не входит в миграцию. Сохранить DigitalHouses/Global/night_mode/state; инвентаризировать старые потребители rev/state, changed/state, changed/author/state и binary_sensor.bs_global_system_boot_completed. Старый HA gate по смыслу соответствовал HA startup, поэтому совместимость через отдельное HA-ready зеркало, а не незаметная подмена строгим общесистемным gate. При импорте legacy-профиля с валидной цветовой температурой явно переносить color_mode=cct и прежнее значение color_temp_kelvin; RGB остается незаданным. Не удалять старые пакеты/топики или прямое управление громкостью до проверки потребителей, переноса значений и согласованного отключения старого производителя. Никогда два авторитетных издателя одного state. При необходимости сохранить legacy entity через минимальный compatibility package без второй бизнес-логики; проверить конфликт entity ID. Не менять другие продукты.

## 10. Приемочные тесты первой версии

- Ручное включение дня среди ночи при auto_switch on; отсутствие самопроизвольного возврата; следующая граница; режим auto_switch off.
- Переход через полночь, перезапуск App, пропущенная граница, восстановление ручного состояния, корректная обработка времени и невалидной конфигурации.
- Изменение из Ingress и HA: единая конфигурация, полные retained profiles, отсутствие лишних events.
- Независимые CCT/RGB профили, проверка enum и трех целых каналов RGB 0..255, отклонение двух одновременно заданных цветов, обязательная очистка противоположного значения при атомарном изменении color_mode и цвета, отсутствие fallback и mode events при редактировании цвета; одинаковый roundtrip через Ingress и HA.
- Повторная команда, MQTT reconnect, HA restart: отсутствие искусственных mode events.
- HA restart при работающих MQTT/Z2M: Modes и независимые функции не прекращаются.
- MQTT restart, stale retained on, loss of App, неправильный nonce, timeout, HA online до готовности интеграции.
- Z2M restart, stale bridge data, health_check failure, недоступное отдельное устройство, пустая сеть.
- Gate закрывается при обнаруженной потере источника; восстановление baseline не производит ложных событий. Реальная неисправность источника видна даже с закрытым gate.
- Проверка отсутствия implicit defaults, корректной валидации схем, публикации событий, rollback migration, DH Sync и стандартных UI/telemetry/release контрактов.

Источники технических механизмов: [HA MQTT](https://www.home-assistant.io/integrations/mqtt/), [HA MQTT Sensor](https://www.home-assistant.io/integrations/sensor.mqtt/), [Z2M MQTT API](https://www.zigbee2mqtt.io/guide/usage/mqtt_topics_and_messages.html). Алгоритм Gate — проектное решение, не результат натурного теста. Интервалы probe/heartbeat, точные служебные топики, поддерживаемая корреляция Z2M и миграция проверяются при реализации; не обещать мгновенное обнаружение потери соединения или полную готовность всех устройств.
