# DigitalHouses Electrica App — целевая архитектура v0.3.0

**Статус:** согласованное направление разработки, 26.11.2026.
**Исходная рабочая версия:** DigitalHouses Aqara Switch App v0.2.3.
**Этот документ описывает цель, а не уже реализованные функции.** Рабочий
код, релиз и установку Aqara сохраняем до готовности нового продукта.

## 1. Назначение и границы

Electrica — управление исполнительными устройствами дома преимущественно
с физических выключателей, батарейных кнопок и панелей (80–90% сценариев
в типовой установке владельца), а также от датчиков, расписаний и общих
действий. Это не универсальный редактор автоматизаций.

| Идентичность | Целевое значение |
| --- | --- |
| Название | DigitalHouses Electrica App |
| Короткое название | DH Electrica |
| Product ID, HAOS slug, каталог | `digitalhouses_electrica_app` |
| HA entity prefix | `dh_electrica_app` |
| Ingress | Electrica |
| GHCR | `ghcr.io/digitalhouses/digitalhouses_electrica_app` |
| Первый целевой релиз | `digitalhouses_electrica_app-v0.3.0` |

Полное переименование выполняется до тиражирования. По [Product Naming
Standard](../../docs/standards/PRODUCT_NAMING_STANDARD.md) новый slug означает
новую установленную сущность Supervisor, а не прозрачное обновление старой.
Исторические теги неизменны. Не требуется перенос старого /data или старых
Supervisor Options; пользователь экспортирует JSON, устанавливает новый App
и импортирует назначения. Проверить совместимость формата экспорта v0.2.3:
не терять параметры и не подменять несовместимые назначения молча.
Старый App и новый App не должны одновременно выполнять те же назначения
или удерживать одни и те же реле. Оформление смены identity, registry, CI,
release, GHCR, telemetry, MQTT Discovery и DH Sync — отдельный этап релиза.
Старые ресурсы DH Sync удаляются/заменяются только по согласованной процедуре
вывода старого продукта; соседние панели и продукты не редактируются
без согласования с их владельцем.

### Ответственность продуктов

| Продукт | Ответственность |
| --- | --- |
| Electrica | Клавиши, Mode Keeper, датчики, исполнительные устройства, таймеры, расписания, общие действия, применение профилей, журнал, machine events |
| DH Presence | Определение присутствия людей/ухода; может вызвать общее действие Electrica |
| DH Climate | Алгоритмы климат-контроля и регулирования; Electrica только вызывает поддерживаемые команды |
| Глобальный режим дома / будущий DH Home Mode | Источник Day/Night, расписание режима и ручное переключение |
| Будущий DH Relay | Электротопология, питающие DIN-реле, фазы L1/L2/L3, контроль линий, каскад питания |
| Будущий DH Voice | Подписка на машинные события, тексты, TTS, язык, колонки, очередь и громкость голосовых сообщений |

DIN-реле как топология, привязки к фазам, восстановление питания и каскады
**исключены** из Electrica. Исторический `panel_relay` и описание каскада
в field-lessons сохраняются как история, не как требования нового продукта.
Обычная управляемая switch-сущность (розетка/вытяжка) остаётся допустимой целью;
это не делает Electrica менеджером питающих линий.
Никаких обязательных зависимостей от будущих приложений, Node-RED, новой
БД или второго брокера. Все функции Electrica, не требующие внешнего
источника, работают без него.

## 2. Архитектура

```text
Z2M inventory / actions + HA registry / states + sun.sun + global Day/Night
                     |
   Keys | Motion/Presence | Schedules | Common actions
                     |
     Rules + capability validation + guards + timers + profiles
                     |
          Shared execution engine + state observation
                  /                     \
       Verified Z2M MQTT           Verified HA API
           devices/groups          native entities/services
                  \                     /
         LOG + observed state + transient domain events
```

Ingress — настройка; App — исполнение; HA Dashboard — отображение.
Один существующий Engine, расширяемый по доменам; не вводить отдельные
несогласованные механизмы отправки команд для каждого источника.
Подтверждённые Z2M маршруты для светильников и групп сохраняются.
HA API используется для проверенных нативных сущностей и поддерживаемых
операций остальных доменов; не обходить проверку Z2M маршрута fallback-ом.
Использовать существующие MQTT-клиент, HA registry, подписки и кеш состояния.
Scan на старте, периодически (существующий интервал 60 минут, 0 отключает)
и вручную из Ingress; Scan не выполняет физические записи. Сохранять
отсутствующие, отключённые и переименованные назначения с диагностикой.

## 3. Клавиши и адаптеры оборудования

Одна физическая панель может содержать несколько независимо настраиваемых
клавиш. Тип определяется для каждой клавиши, не для устройства целиком.

| Тип | Управление | Aqara | Actions |
| --- | --- | --- | --- |
| Физическая | Собственное реле, локальная работа | control_relay | **Нет** |
| Логическая | Назначенные сущности | decoupled | Только фактически объявленные/поддерживаемые события |

Батарейная кнопка и панель без встроенного реле — логические, Mode Keeper
не нужен. У физической клавиши нельзя назначать single/double/hold и другие
Actions: её локальное переключение не должно конфликтовать с Engine.
Опциональный таймер выключения физической нагрузки начинается от наблюдаемого
ON её собственного реле, не от события нажатия.

Mode Keeper удерживает заданный режим на поддерживаемых клавишах: физическая
— control_relay (без принудительного изменения состояния реле); логическая —
decoupled и отдельно «Удерживать» ON либо OFF. В Ingress ровно два выбираемых
типа клавиши; поле удержания показывается только у логической проводной
клавиши. Батарейные кнопки логические без поля удержания. Новую логическую
клавишу сохранять только после выбора ON/OFF. Старый decoupled без удержания
и ещё не настроенные клавиши не менять автоматически. Не включать
неиспользуемые выходы автоматически. Для Aqara сохранять проверку capabilities,
координатора, IEEE, совместимого fingerprint и свежего состояния, задержку
восстановления, безопасный Maintenance (локальный режим без изменения питания).
Политика задаётся явно пользователем. Недоступное/неизвестное состояние не
является основанием для слепого включения. Аппаратная приёмка проводных
Aqara отложена до получения выключателей.

Бренд не является фильтром всего приложения. Базовый адаптер принимает
проверенные Z2M Actions, специфический адаптер отвечает за режимы, соответствие
физических клавиш и реле, особенности конкретной модели. Начать с Aqara и
подтверждённых event-only устройств, расширять по фактическим возможностям;
не обещать поддержку произвольных моделей и не менять существующий Zigbee
binding автоматически. Не исполнять события физической клавиши.
Если измеритель мощности есть, показывать W **на уровне устройства**,
не на уровне клавиши; unknown/unavailable = — W, нет измерителя = скрыть
поле. Не вычислять мощность отдельных нагрузок из общей.

## 4. Назначения и домены

Один Action содержит один или несколько адресных назначений, каждое со
своей операцией, параметрами и опциональным таймером; смешанные домены
допустимы. Пример: single — Toggle света, double — ON вытяжки на 30 минут,
triple — Play радио, hold — OFF света и вытяжки + Stop музыки.
Повторение одного события не должно порождать лишние команды.

Инженерный «Тест» у светильника в Entity Picker и редакторе назначения:
одна явная команда ON ↔ OFF через существующий Engine, с проверкой
маршрута и наблюдаемого состояния, без изменения привязок и без эмуляции
нажатия клавиши. LOG: TEST. Отправка не считается подтверждением; повторный
тест блокируется до результата предыдущей команды. Недоступная цель или
глобальный Maintenance блокируют тест. Группа проверяется как одна
подтверждённая групповая сущность, не как индивидуальный ACK каждого участника.

| Домен | Операции (только если поддерживаются конкретной сущностью) |
| --- | --- |
| light | Toggle, ON, OFF; яркость, CCT или RGB, transition |
| switch | Toggle, ON, OFF |
| cover | Toggle, Open, Close, Stop, Position |
| climate | Toggle/ON/OFF если доступно, HVAC mode, temperature |
| media_player | Play/Pause, Play, Pause, Stop, Next/Previous, volume, воспроизведение выбранного медиа |

Для cover Toggle однозначно разрешать из подтверждённого состояния; не
угадывать неизвестное состояние и не обходить защиту. Climate: не изобретать
режимы HVAC, температуры, presets; использовать capabilities и допустимые
границы. Media: только доступные операции; не запускать проигрывание
ради регулирования громкости. Никаких произвольных строк HA service или MQTT
topics, пользователь выбирает сущности и операции из каталога.
Сохранять атомарную запись назначений, capability validation, контроль
верификации маршрута, skip offline, общий согласованный Toggle для света
(не инвертировать хаотично разнородную группу), исключение дублирования
участников Zigbee groups. Не считать групповое состояние доказательством
состояния каждого участника.

## 5. Профили и глобальный режим

Источник режима на первом этапе — существующий retained MQTT
`DigitalHouses/Global/night_mode/state`, on = ночь, off = день.
Это текущий факт, не Event. В старом HA-пакете night_mode_global_package
уже есть ручное переключение, расписание и публикация состояния.
Не менять пакет, пока не проверены все потребители. Нет валидного режима —
не выдумывать день/ночь, отразить проблему; независимые назначения работают.

- ON/OFF — фиксированный сценарий, компактный интерфейс, без портянки
  параметров света; по умолчанию для клавиш. Если параметры сохранены в
  старом JSON, не терять их; компактное представление фиксированных
  параметров/совместимость проверить перед релизом.
- День/Ночь — преимущественно для датчиков, опционально для клавиш.
  Общий профиль дома и опциональное индивидуальное переопределение
  (предложение, значения задаёт пользователь): яркость, CCT либо RGB,
  transition, для media_player — громкость.
- Астрономия — отдельный источник расписания; показывать световые параметры
  только когда применимы. Не смешивать календарь с выбором операции.

Опциональная настройка **«Изменять включённый свет при смене режима»**:
для участвующих в Day/Night назначениях и только уже включённых устройств
изменять яркость и CCT/RGB, с transition при поддержке. OFF остаётся OFF,
фиксированные назначения не меняются, недоступные пропускаются.
Проверять фактические состояния членов группы перед адаптацией: group ON
не разрешает включить выключенных участников. При пересечении назначений
не отправлять дубли и не угадывать конфликтующие профили.
Аналогичная опция для громкости активных media_player; не запускать музыку.
Если адаптация выключена, новые параметры применяются при следующем
соответствующем включении. Смену режима и итог фиксировать в LOG.
Глобальные расписания Day/Night и TTS не входят в Electrica.
Старую автоматизацию громкости отключать только после осознанного перехода
на управление Electrica, чтобы избежать двух владельцев одного параметра.

## 6. Motion / Presence / Lux и таймеры

Выбирать совместимые датчики независимо от производителя. Учитывать
реальные классы/возможности motion, occupancy/presence, illuminance.
Lux поле показывать только если датчик действительно предоставляет
освещённость в lx; не выдавать raw illuminance/неизвестную единицу за lux.
При наличии Lux пользователь задаёт числовой порог (например 70 lx или
50000 lx); отдельный флаг использования Lux не нужен. Автоматический ON
только при lux < threshold; 0 не разрешает включение, 50000 — высокий,
но не безусловный порог. Нет Lux у датчика — нет условия. Есть порог,
но измерение неизвестно/недоступно/неактуально — автоматический ON пропустить.
Проверять освещённость только на входе, не выключать свет из-за повышения
Lux от собственного светильника. Ручное управление имеет приоритет.

Авто-OFF — независимая опция, по умолчанию не включать:
- клавиша/физическое реле: отсчёт от включения (например вытяжка 30 мин);
- motion/presence: отсчёт от подтверждённого отсутствия, повторное
  обнаружение отменяет таймер; пока присутствие есть, авто-OFF не срабатывает;
- явный OFF/Stop отменяет соответствующий таймер; ручное включение не
  должно быть неожиданно отменено старым таймером чужого назначения.
Не отсчитывать отсутствие от unavailable. Согласовывать несколько
назначений одной цели; защищать ручное состояние, не запускать циклы.
Сохранять активные дедлайны для безопасного восстановления после рестарта
(в том числе вытяжки), проверять актуальность цели и принадлежность таймера
прежде чем отправлять просроченную команду. Правила разрешения коллизий и
длительность ручного приоритета уточнить до реализации; не добавлять
сложный универсальный DSL.

## 7. Расписания и защитные условия

Универсальный источник: локальное время, рассвет, закат, signed offset
в минутах, время и timezone из HA. Учитывать переход суток и timezone.
Пример: закат -15 min ON наружного света, рассвет +20 min OFF; для штор
рассвет +30 min Open, закат Close; обычное расписание 08:00 Open.
Использовать авторитетные астрономические данные HA (sun.sun); учитывать
следующие события и пересчёт на границах суток. Не вычислять по догадке
при отсутствии исходных данных. Для явно заданного интервала наружного
света предусмотреть восстановление требуемого состояния после перезапуска;
не воспроизводить пропущенные команды ворот/штор вслепую.

Опциональная блокировка движения cover по одному или нескольким
оконным binary_sensor (window/door/opening по подтверждённым capabilities):
если хотя бы одно окно открыто, состояние неизвестно или датчик недоступен,
не разрешать Open/Close/Position/движущий Toggle. Применять ко всем
командам приложения, в том числе от клавиши, расписания, общего действия.
Stop не блокируется. На этапе клавиш датчики сохраняются в назначении cover,
при исполнении используется объединение защит всех сохранённых назначений
этой цели, в том числе отключённых и отсутствующих клавиш. Toggle в движении
не угадывает направление; пользователь может назначить явный Stop.
Не возобновлять пропущенное движение при закрытии
окна автоматически. Штатная аппаратная защита ворот/гаражей обязательна;
программная проверка — дополнение, не замена. Не обходить защиту и не
выдавать состояние команды за подтверждение физического движения.

## 8. Общие действия и HA groups

Именованный набор команд, вызываемый клавишей, расписанием, вручную
из Ingress или внешним событием (например DH Presence — уход людей).
Не определять факт ухода внутри Electrica. Вызов — отдельный command
контракт MQTT, не повторная публикация факта состояния, не retained;
точное имя топика и схема будут согласованы при реализации.
Обычные HA light/cover и иные группы можно выбирать, если их поддержка
проверена; состав Z2M groups брать из bridge/groups, не копировать вручную.

Пример «Уход из дома»: все lights OFF, выбранные вентиляторы OFF, media
Stop. Динамическая цель «Все light.*» с явными исключениями (наружное,
аварийное освещение и т.п.) вычисляется на момент выполнения.
Для общих OFF дедуплицировать пересекающиеся HA/Z2M группы и отдельные
устройства, учитывать исключённых членов, выбирать безопасный маршрут,
проверять наблюдаемое состояние отдельных доступных участников, повторять
OFF ограниченно для оставшихся включённых; не скрывать unknown/offline.
Гарантировать выключение недоступного устройства физически нельзя.
Обычные группы HAOS не требуется создавать вручную ради каждого сценария.

## 9. Ingress, хранение и наблюдаемость

Стиль Network App, компактная полноширинная компоновка, основной экран
«Клавиши», дополнительно «Датчики», «Расписания», «Общие действия»,
«Профили». В шапке Scan, экспорт, импорт, JSON, LOG. На основном экране
устройство → типы клавиш → краткие action/target summaries; вся строка открывает
настройку. Z2M friendly_name — отличающееся имя устройства HA (name_by_user/name). Физические клавиши без Actions. Мощность на уровне устройства.
Отдельные пиктограммы доменов, групп, текущего состояния и проблем.
Редактор показывает только параметры выбранного сценария и capabilities;
ON/OFF без развёрнутых настроек яркости/цвета. Единственное явное Save,
атомарное применение без перезапуска. Нет управляющих YAML в HAOS.

Entity Picker по образцу DH Climate
(`dh_climate_app/src/dh_climate_app/web/entity_picker.js`):
поиск по имени/entity_id/комнате/устройству; фильтры домена, комнаты,
интеграции, доступности; предвыбор комнаты устройства; множественный
выбор, состояние, место использования, сохранение отсутствующих и
выбранных за пределами фильтра сущностей. Подбор датчиков — классы и
единицы; подбор целей — совместимые домены. Выбор редактирует форму,
не вызывает сервис. Реализация в коде Electrica, без изменения DH Climate.

Один локальный конфигурационный JSON, схема с версией, атомарный экспорт/
импорт, просмотр JSON, явная валидация, без секретов. Системные параметры
остаются в Supervisor Options. Не смешивать пользовательские назначения
с обнаруженной топологией/временными состояниями и журналом.
Сохранить рабочую механику v0.2.3: LOG закрыт по умолчанию, справа ~50%,
одна строка на исходное событие с несколькими целями, локальное время HA,
500 записей / 24 часа в RAM, без БД, инкрементальная выдача, подсветка
нажатий и состояния. ✓ — отправлено/сервис принял; ✓✓ — наблюдаемое
соответствующее состояние; ⚠ — пропуск/нет подтверждения с причиной.
Не считать Z2M optimistic state или HA service acceptance физическим ACK.
Для операций без наблюдаемого результата не рисовать ✓✓ по умолчанию.
Для параметров (яркость, CCT, громкость, position, temperature) подтверждать
соответствующее значение, а не только ON. Существующий таймаут 90 сек —
базовый; не выдавать завершение длительного движения cover преждевременно.

## 10. Машинные события и DH Voice

Electrica публикует машинные факты; не содержит настроек голосовых текстов,
TTS, выбора колонок для уведомлений, локализации или маршрутизации
голосовых сообщений. DH Voice (отдельный будущий продукт) подписывается
и сам решает, что, где и когда озвучить. Управление музыкой/громкостью
по клавишам/профилям остаётся в Electrica, голосовая доставка — в Voice.

Предложенная доменная маршрутизация:
```text
DigitalHouses/Global/events/light
DigitalHouses/Global/events/switch
DigitalHouses/Global/events/cover
DigitalHouses/Global/events/climate
DigitalHouses/Global/events/media_player
```
system и события иных продуктов — дальнейшее отдельное согласование.
QoS 1, retain=false. Не воспроизводить историю при старте, дедуплицировать
QoS1 повторную доставку по стабильному ID события. State отдельно от Event.
Публиковать факт только после наблюдаемого перехода/изменения; различать
отправленную команду и полученное состояние. Не заявлять о физическом
подтверждении при optimistic state. Не публиковать фиктивные transitions
на стартовом снимке, retained replay, reconnect или повторном неизменном
отчёте. Предпочтительный порядок: авторитетный state -> retained state
(если применяется) -> transient event.

Согласовать реализацию с существующим
[Events & Notifications Standard](../../docs/standards/EVENTS_AND_NOTIFICATIONS_STANDARD.md)
и [Contract Data Policy](../../docs/standards/CONTRACT_DATA_POLICY.md):
отдельная machine schema для каждого event_type, MQTT Event Discovery
там, где применимо, без универсального notification envelope.
Пример целевого контракта climate_state_changed (проект, не выпущенный API):
```json
{
  "schema_version": 1,
  "event_type": "climate_state_changed",
  "event_id": "unique-occurrence-id",
  "source": "digitalhouses_electrica_app",
  "entity_id": "climate.bedroom",
  "previous_state": "heat",
  "state": "off",
  "trigger": "aqara_bedroom.single_left",
  "observed_at": "2026-11-26T00:15:00+05:00"
}
```
Доменные схемы определяют обязательность полей (например trigger только
когда причинная связь действительно установлена); не подставлять неизвестные
данные. Для cover различать opening/open/closing/closed. Voice может
озвучить climate.bedroom -> off как «Климат-контроль в спальне выключен»,
но этот текст отсутствует в MQTT producer payload.
Не вводить второй локализованный notification event, адаптер или
обязательную подписку Voice. Не менять общий стандарт и чужие продукты
в рамках этой разработки. Межпродуктовое принятие доменных топиков и
правила единственного producer при пересечении Electrica/Climate/Voice —
отдельное согласование до стабилизации контракта DH Events.

## 11. DH Sync, delivery и тестирование

Следовать [DH Sync](../../docs/standards/DH_SYNC_DEVELOPER_STANDARD.md),
[Unified Product Status Card](../../docs/standards/UNIFIED_PRODUCT_STATUS_CARD_STANDARD.md),
[Operation UI](../../docs/standards/OPERATION_UI_STANDARD.md),
[Manual Refresh](../../docs/standards/MANUAL_REFRESH_STANDARD.md) и действующим
release/telemetry правилам. Новый ID в /sync, QoS1 retained на каждом
connect/reconnect; schema, product_id, type, version, repository, product_path.
Canonical view в dashboards/ru, пакеты по действующему стандарту;
панели принадлежат DH Sync. Телеметрия Apps остаётся opt-in.
Никаких изменений чужого кода ради интеграции без отдельного задания.

### Предлагаемый порядок реализации (не отдельные обязательные релизы)

1. Закрепить модель конфигурации и identity; сохранить рабочий Engine,
   тесты v0.2.3, JSON import/export и LOG.
2. Клавиши physical/logical, адаптер Aqara, общий Entity Picker,
   пять доменов и смешанные назначения.
3. Датчики, lux, опциональные таймеры, профиль Day/Night и адаптация
   включённых светильников / активных колонок.
4. Расписания, защитные условия cover, общие действия и OFF reconciliation.
5. Доменные Events, документация, канонический dashboard/Sync,
   registry/CI/immutable delivery; выпустить Electrica после приёмки.

Acceptance: существующие одиночные и групповые light toggles и JSON v0.2.3
не деградируют; нет Actions для physical; смешанный hold выключает свет,
вытяжку и останавливает медиа; Motion/Presence с Lux и без; таймеры
опциональны и сохраняются безопасно; Day/Night не включает выключенное;
блокировка окна при open/unknown/unavailable действует на все источники;
астрономия с signed offset, сменой суток, restart; дедупликация групп и
исключения all lights; ✓✓ только по наблюдаемому результату; QoS1 non-retained
events без TTS; стандартные CI/repository checks и smoke test на HAOS.
Проводные Mode Keeper, фактическая работа cover/climate/media, реальное
освещение и аппаратная безопасность требуют натурной проверки.

### Не входит в текущую реализацию

DH Relay / каскады / фазы / питающая топология; DH Voice и общий глобальный
Event Bus стандарт для остальных продуктов; перенос глобального night_mode
пакета; переписывание DH Climate, DH Presence, DH Sync. Не разрабатывать
автоматическую миграцию установки Aqara. Точные границы профилей,
legacy fixed parameters, разрешение конфликтов/ручного приоритета и
окончательные event/command schemas уточняются в рамках реализации;
не считать открытые технические решения уже согласованными API.
